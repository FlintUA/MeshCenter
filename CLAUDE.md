# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MeshCenter is a Flask web control center for a Meshtastic LoRa radio attached to a Raspberry Pi over USB serial or Bluetooth LE. The MIT-licensed Core (`server.py`, `api/`, `meshsrv/`, everything except `adapters/`) never imports the `meshtastic` Python package directly - all real radio I/O goes through a neutral `RadioTransport` interface (`meshsrv/radio_transport.py`, "Backend Protocol v1") implemented by `SerialTransport`/`BLETransport` in `adapters/meshtastic/`, which run in a separate subprocess with its own Python venv specifically to keep the GPLv3 `meshtastic` dependency isolated from Core's own process (see "GPLv3 process isolation" below and `THIRD_PARTY_NOTICES.md`). Core's own listener (`meshtastic --listen`, still a subprocess, still parsed line-by-line - "Stage A" of the isolation work, see below) is the one exception: it shells out to the CLI binary as an arm's-length subprocess, the same license-safe reasoning as any other external tool invocation, never importing the Python package. There is no database - all persistence is local JSON files (one SQLite file for waypoints) under `data/`.

## Running it

There is no build step, package.json, or linter config in this repo - don't invent `npm run` or lint commands that don't exist here. There **is** a pytest test suite (`tests/`, `pytest.ini`) and a GitHub Actions CI workflow (`.github/workflows/ci.yml`) - see "Testing" below.

```bash
python3 -m venv --system-site-packages venv   # --system-site-packages required for Picamera2 on the Pi
source venv/bin/activate
pip install -r requirements.txt

cp config.example.py config.py                # edit MESHTASTIC_PORT / LOCAL_NODE_ID / LOCAL_NODE_NAME
mkdir -p data

python server.py                               # dev run, http://<host>:5000
# or, in production:
sudo systemctl restart meshcenter.service       # runs gunicorn - see "Deployment" below
```

`config.py` and `weather_secrets.py` are gitignored local files; `server.py` exits at import time if `config.py` is missing or missing required variables (see the `required_vars` check near the top of `server.py`). When changing code that reads config, check `config.example.py` for the authoritative variable list.

### Testing

```bash
pip install -r requirements-dev.txt   # adds pytest on top of requirements.txt - never installed on a production Pi
pytest                                 # run from the repo root; picks up pytest.ini automatically
```

`tests/conftest.py` makes `server.py` importable without a Pi or a radio attached (a synthetic `config.py`, a fake Meshtastic CLI/serial port, a stub for the Pi-only `libcamera` import) - it does **not** start `start_runtime()`'s background threads/radio listener, so the suite is safe to run anywhere, including CI. As of PR #69 this covers CLI-output parsing, `normalize_settings()`, node ID validation, `sanitize_text()`, the auth/message-queue/radio-identity/profile-manager logic, and the gunicorn runtime lock - not full end-to-end coverage, but a real regression net. Run `pytest` locally before opening a PR.

`.github/workflows/ci.yml` runs on every PR and push to `main`: `python -m compileall` (all Python), `bash -n` on every installer/deploy shell script, `node --check` on the non-vendored `static/*.js` files, `scripts/check-i18n.py` (all four locale catalogs define the same keys), `scripts/check_startup_calls.py` (server.py's `__main__` block still calls every required background worker/route-registration - a static text check, not a real test, guarding against the exact class of regression that prompted it: a stale-branch deploy silently dropping a startup call with no exception raised), then `pytest`. It does not run linters (none configured) or touch real hardware.

Beyond that, manual verification against a real or simulated radio (`meshtastic --port <dev> --info`) and exercising the REST endpoints/UI in a browser is still how anything touching the actual radio listener, camera, or e-Paper hardware gets validated - the test suite deliberately doesn't attempt to fake real hardware I/O for those.

## Architecture

### `server.py` is the core, not a thin entrypoint

`server.py` (~6,100 lines) owns the Flask `app`, nearly all shared mutable state (`nodes`, `messages`, `chats`, `settings`, locks, background threads), and most route handlers that haven't yet been split out. Newer feature areas live in `api/*.py`, but they are **not Flask Blueprints** - each is a plain function `register_<area>_routes(app, state_lock, ..., <30+ shared globals/functions>)` called from `server.py`, closing over the objects/functions passed in. When adding a new route module, follow this dependency-injection-by-parameter-list pattern rather than introducing Blueprints, and wire the new `register_*_routes(...)` call into `server.py`.

The project's own stated direction (see README "Modular Architecture") is to keep shrinking `server.py` by moving logic into `api/`, `meshsrv/`, `storage/`, `telemetry/`, `camera/` - prefer extending those modules over growing `server.py` further when the code is genuinely a separate concern.

### The radio link: listener stays in Core (Stage A), everything else crosses a process boundary

`listen_meshtastic()`/`run_listener()` in `server.py`/`meshsrv/serial_port_supervisor.py` still runs `meshtastic --listen` as a subprocess and classifies each stdout line by substring checks (`"NODEINFO_APP"`, `"TELEMETRY_APP"`, `"WAYPOINT_APP"`, `"TEXT_MESSAGE_APP"`, etc.), handing multi-line blocks to parsers like `process_nodeinfo`, `parse_telemetry_from_listen_line`, `parse_waypoint_from_listen_line`. This is fragile by nature (depends on the CLI's human-readable log format) and, as of the process-isolation work, deliberately still lives in Core ("Stage A" - a full move to the adapter process is "Stage B", not yet done). It only ever shells out to the `meshtastic` CLI *binary* (an arm's-length subprocess invocation, not a Python import), so it doesn't break the GPLv3 isolation below.

Everything else - connect/disconnect/reconnect, sending, `get_nodes`/`get_channels`/`get_local_node`/`get_metadata`, `set_device_time`, BLE scan - goes through `meshsrv/radio_transport.py`'s `RadioTransport` ABC ("Backend Protocol v1"), implemented by `SerialTransport`/`BLETransport` in `adapters/meshtastic/` (the only modules anywhere in the repo that import the `meshtastic` Python package - lazily, inside the method that needs it). `meshsrv/transport_router.py`'s `TransportRouter` is the single, stable object every DI consumer (`api/api_chat.py`, `api/api_waypoints.py`, `meshsrv/schedule_engine.py`) actually calls - it wraps whichever concrete transport is currently active and handles switching between them (`api/api_meshtastic.py`), so callers never need to know or care which transport is live.

### GPLv3 process isolation - why, and how it actually works

The `meshtastic` Python package is GPLv3-licensed; MIT-licensed Core code must never import it directly (see `THIRD_PARTY_NOTICES.md` and `adapters/meshtastic/LICENSE`). `SerialTransport`/`BLETransport` run in a **separate OS process**, with their own **separate Python venv** (`adapters/meshtastic/venv`, created by `install.sh`'s `step_adapter_venv()`/`meshcenter-firstboot.sh`, installing `adapters/meshtastic/requirements.txt`) - Core's own venv/`requirements.txt` has no `meshtastic` dependency at all. Process isolation (not merely code-directory separation) is the architecture chosen so GPLv3 code never links into Core's MIT-licensed process - see README's licensing section for the reasoning.

- `meshsrv/adapter_ipc_client.py`'s `AdapterSupervisor` spawns/supervises the adapter subprocess (`python -m adapters.meshtastic.ipc_server`, one persistent process, multiplexing both serial and BLE per-request via a `transport_type` field) and talks to it over newline-delimited JSON on stdin/stdout (`meshsrv/ipc_protocol.py`, `docs/BACKEND_API.md`'s wire shape). `AdapterIPCTransport` is the Core-side `RadioTransport` implementation that does the actual request/response round-trip - `server.py` constructs one instance per transport type (`serial_ipc_transport`, `ble_ipc_transport`) and wires them into `TransportRouter`.
- **Three-tier timeout contract** (see `meshsrv/adapter_ipc_client.py`'s module docstring for the full detail): (a) the adapter's own internal `TimeoutEnforced` watchdog (`adapters/meshtastic/_timeout_support.py`) uses the caller's timeout minus a fixed margin, so it can report its own graceful timeout before (b) `AdapterSupervisor.call()`'s own deadline fires and SIGKILLs the adapter subprocess, which is itself bounded by (c) `TransportRouter`'s caller-declared budget, split dynamically (`time.monotonic()`-measured, not a fixed proportion) between lock-wait and the delegated call. A killed adapter respawns automatically on the next call - no data loss, no stuck state, just a `TransportError(TIMEOUT)` to the caller.
- **`claim_exclusive_access()`** (`meshsrv/serial_port_supervisor.py`'s `SerialPortSupervisor`, called on Core's own listener-management instance before any serial-type IPC call - renamed from `claim_for_external_command()` during a later stabilization pass, once the same method turned out to be used by `SerialTransport`'s own send/get methods too, not just "externally"; see that module's own docstring) pauses Core's `--listen` subprocess and confirms the port is genuinely free before letting the adapter open its own `SerialInterface` - a live-caught gap, not part of the original design, closed after Core's listener and the adapter's own operations raced for `/dev/ttyACM0` with nothing coordinating them.
- The listener-management logic itself (`run_listener()`, `get_listener_pid()`, `claim_exclusive_access()`, and the port/subprocess-management internals) lives in `meshsrv/serial_port_supervisor.py` - MIT, stdlib-only, no `meshtastic` import - not in `adapters/meshtastic/`. `SerialTransport` composes one of these instead of implementing that logic itself (used by both Core's own listener-management instance and, separately, `SerialTransport`'s own per-call claim on the adapter's own instance); `server.py` composes its own directly and no longer imports anything from `adapters/` at all - this is what actually closed the audit's P0 #1 finding (a class from a GPLv3-labeled directory being imported straight into Core), not just a docstring claim.
- Orphaned-adapter protection if Core itself dies: `deploy/meshcenter.service`'s `KillMode=control-group` (systemd's default, live-confirmed via `systemctl show`) plus `PR_SET_PDEATHSIG` (`preexec_fn`, Linux-only) for the `python server.py` direct-run case outside systemd.
- BLE cleanup on a killed adapter: `bluetoothctl disconnect <address>` from Core's own process (arm's-length CLI call, not a library import) when the kill happened mid-BLE-operation - a BLE GATT session can outlive the process that opened it.

### Known, accepted trade-offs (not bugs - explicitly documented, some deferred on purpose)

- **TCP receives text, waypoints, NodeInfo, positions, telemetry and routing ACKs** (best-effort, duplicates suppressed Core-side): no remote waypoint deletion, and an event captured while the link is down or buffered in an adapter process that is killed before the next drain can be lost. Everything else about the radio still comes from the periodic snapshot / manual actions.
- **BLE receive-blindness**: while Bluetooth is the active transport, MeshCenter can send but cannot receive - no incoming messages/telemetry/nodeinfo at all, not degraded, fully absent. Core's listener only ever manages the *serial* `--listen` subprocess; there is no BLE equivalent yet ("Stage B" work). Surfaced explicitly in the UI (`meshtastic_ble_receive_warning` in the i18n catalogs) and in the README's Bluetooth section - don't let this regress silently if BLE receive is ever implemented.
- **Hot-reconnect after a physical serial cable swap - RESOLVED (H2-C, PR #331, see `KNOWN_ISSUES.md` KI-008):** `meshsrv/serial_port_supervisor.py`/`meshsrv/serial_reconnect.py` detect a genuine disconnect (the Meshtastic library's own stdout warning, or a changed/missing device node via `DeviceIdentity` - USB enumeration (`usb_busnum`/`usb_devnum`) as the primary signal, `(st_rdev, st_ino)` as a fallback when sysfs is unavailable, since inode reuse alone is unreliable), resolve the radio's `/dev/serial/by-id/*` link so a changed `/dev/ttyACMx` number doesn't matter, and re-verify identity with a real `--info` probe before resuming - a pre-Popen invariant (`_verified_device`, set only by a fresh MATCH or `mark_device_verified()` at boot) additionally guards every restart attempt, not just ones the stdout marker or a health-tick already flagged, so a plain nonzero-exit crash or a by-id-fallback landing on a different device can't reach `Popen` unverified either. A boot-time identity failure now enters the same wait-and-recheck state machine (`start_in_recovery_state()`) instead of permanently disabling recovery; `on_serial_identity_match()` is the one idempotent hook (in `server.py`) that starts the four listener-dependent workers and runs the one-time `--info` seeding exactly once per process lifetime, whether identity matched at boot or only resolved later via a live replug - without it, a boot-in-recovery radio that later matched stayed invisible (no telemetry, no seeded node/base-status data) until a full restart, even with the listener itself running. `/api/restart_listener` and `/api/radio_connection/reconnect` both force a fresh identity re-check rather than trusting a stale pre-release/pre-mismatch result (`clear_mismatch()`); `/api/radio_connection/release` and `/api/radio_connection/reconnect` are refused outright (`serial_only_action_refusal()`, HTTP 409) for a TCP/Bluetooth radio, since both delegate to serial-only machinery (`listener_supervisor`) that does nothing meaningful for those transports. The separate adapter subprocess (send/`get_channels()`) tracks the listener's current verified port too (`current_serial_port()`/`on_port_changed()`), so it no longer keeps retrying a stale path after a real device-path change. Live-verified on dev (192.168.2.104, 2026-10-04): same-path replug, `ttyACM0→ttyACM1` renumbering, and a forced path change mid-adapter-call all recovered correctly, including a 30-minute quiet-period A/B against `main` confirming no regression (`KNOWN_ISSUES.md` KI-009). **Not yet live-verified: a different physical radio appearing on replug (the identity-MISMATCH path)** - covered by the automated test suite but no second USB radio was available for a live round; if a different radio is detected, the listener halts (no automatic resume) and shows "A different radio was connected" in the System Log and as a notification - use **Reconnect Radio** (`Settings > Meshtastic Radio`) once you've confirmed which radio should actually be plugged in, or switch profiles if you intend to use the new one.
- **`radio_lock` bounded, but `prepare_radio_command()`'s own phase is not** (`server.py`'s `radio_session()`): the lock-acquire step is bounded and raises `RadioBusyError`/HTTP 503 on contention, but `prepare_radio_command()` (pause+stop+wait-for-port-release) still runs *before* the bounded acquire, unlike `_claim_radio()`'s deliberate whole-span lock hold - two concurrent callers can still race during that phase. Flagged, not fixed - a separate, narrower follow-up.
- **Telemetry history flush is debounced (H1-C5)**: `add_telemetry_record()`/`add_node_telemetry_record()` (`telemetry/telemetry.py`) only mark history dirty; `telemetry_flush_worker()` writes at most once every `TELEMETRY_FLUSH_INTERVAL_S` (60s) while dirty, with the snapshot taken under `_telemetry_lock` but the actual `json`/disk write happening outside it, so a slow SD-card write never blocks an ingest thread. `shutdown_telemetry()` (registered via `atexit`, since there is no `stop_runtime()` counterpart to hook into) performs one final flush on a clean exit. Accepted trade-off: a crash (not a clean restart) can lose up to ~60s of telemetry *history* - live values (`telemetry_current`, node metrics) are unaffected, and no other JSON-backed store in this project uses this debounced path. `telemetry_history.json` is also the one file written with compact (`indent=None`) JSON (`storage/json_store.py`'s `safe_write_json()` `indent` parameter) rather than the `indent=2` every other file still gets, since it is rewritten whole on every flush and can grow into the tens of thousands of records.

Background threads (`listen_meshtastic`, `telemetry_worker`, `telemetry_flush_worker`, `radio_health_worker`, `cpu_history_worker`, the chat send-queue worker in `api/api_chat.py`) all run for the lifetime of the process. `pause_listen.is_set()` must be respected by anything that wants exclusive serial access, and `state_lock` guards the in-memory JSON-backed state (`nodes`, `messages`, `chats`) during concurrent reads/writes.

### Multi-radio profiles

MeshCenter supports switching between physical Meshtastic radios and keeps each one's data isolated:

- `meshsrv/instance_manager.py` (`instance.json`) tracks this MeshCenter installation's identity and which profile is currently active.
- `meshsrv/radio_identity.py` detects the connected radio and compares it against the configured/accepted one (`MATCH` / `MISMATCH` / `NOT_FOUND`) - the listener refuses to start (`RADIO_IDENTITY_RESULT.status != "MATCH"`) until identity is verified, to avoid silently mixing one radio's data with another's.
- `storage/profile_manager.py` (`ProfileManager`) owns `data/profiles/<8-hex-node-id>/`, one directory per radio, each with its own `messages.json`, `nodes.json`, `sensors.json`, `chats.json`, `deleted_dm.json`, `telemetry_history.json`, `waypoints.db`, `node_icons/`. It also migrates pre-profile legacy flat files in `data/` into the first profile on upgrade.
- Switching profiles (`/api/node-manager/radio/accept`, `/api/node-manager/profiles/<id>/activate` in `server.py`) ends with `_restart_meshcenter_after_profile_switch()` - the process restarts itself so every module rebinds its file paths to the newly active profile rather than trying to hot-swap in-memory state.

Only `data/instance.json`, `data/settings.json`, and `data/screenshots/` are instance-scoped (not per-radio); everything else profile-scoped lives under `data/profiles/<id>/`.

### Storage conventions

- `storage/json_store.py` (`safe_read_json` / `safe_write_json`) is the standard atomic JSON read/write (F4.1 rewrite: a uniquely-named `tempfile.mkstemp()` temp file per write - never a shared fixed `<file>.tmp` name, which let a concurrent read delete an in-flight writer's own temp file out from under it - then `fsync` + `os.replace`; a corrupt file on read is quarantined to `<file>.corrupt-<timestamp>` rather than silently overwritten) - use it for any new JSON-backed state instead of open()/json.dump directly. Callers that mutate shared in-memory state before saving must snapshot-and-restore on a failed write (`storage_write_failed`), not just check the return value - see F4.1 PR 2. `safe_write_json()` also takes an optional `indent` parameter (default `2`, unchanged for every existing caller) for a compact encoding - `telemetry_history.json` is the one caller that opts into `indent=None` (H1-C5), since it's rewritten whole on every flush.
- Two documented exceptions to "everything is JSON": `storage/waypoint_store.py` (`waypoints.db`, per radio profile) and MCAttach's `meshsrv/attachments/db/` (`data/mca/<principal-id>/attachments.db`, keyed by MCA principal, not a radio profile - see `docs/architecture/ADR-0003-attachments-sqlite-exception.md`) - both SQLite, both because their data needs query/transaction patterns a JSON file doesn't fit well.
- `storage/device_manager.py` tracks per-profile auxiliary device/sensor metadata separate from the node list.

### Subsystem modules

- `camera/camera_manager.py` is the live dispatch point for `/video_feed` and `api/api_camera.py` (cutover completed 2026-08-17) - it holds the active `CameraDriver` (`camera/csi_driver.py` for Picamera2-based CSI cameras, `camera/usb_driver.py` for USB/UVC) and handles discovery/dedup/switching across multiple simultaneously-connected cameras. `camera/camera.py` itself still provides the CSI capture internals and the driver-agnostic screenshot helpers (`get_screenshot_day_dir`/`make_screenshot_filename`/`cleanup_old_screenshots`) shared by both drivers, but is no longer called directly for the live stream. Needs the venv built with `--system-site-packages` to see system Picamera2/libcamera bindings.
  - `camera/usb_driver.py` (CAM-1, audit review finding F10, 2026-09-30) drives `ffmpeg` and `v4l2-ctl` as **external subprocesses** - the same arm's-length reasoning as the `meshtastic` CLI - instead of importing `linuxpy`/`v4l2py` (GPL-3.0-or-later) directly into Core's process, which is what it did before. One persistent `ffmpeg` subprocess per active camera serves every `stream_mjpeg()` viewer and (when the resolution already matches) `capture_photo()` from a shared `_last_frame` buffer, parsed out of the subprocess's stdout by SOI/EOI markers; `camera/v4l2_ctl_parse.py` holds the pure-function `v4l2-ctl` text parsers (discovery, formats/resolutions, controls). **Gotcha, confirmed live (CAM-0):** `ffmpeg` exits with code **0** - not an error - when the camera is physically unplugged mid-stream, typically within ~250ms; a deliberate stop exits differently. Exit code alone cannot distinguish the two, so the driver tracks `self._stop_requested` explicitly instead of trusting the raw exit code (see that module's own docstring for the full reasoning). Reference hardware this was verified against: a Microsoft USB3.0 HD CAMERA (YUYV-only, no MJPEG) on camtest - MJPEG passthrough is implemented and unit-tested but not live-verified against a real MJPEG camera. `ffmpeg`/`v4l-utils` are system packages (`install.sh`/`meshcenter-firstboot.sh` install both unconditionally), not a pip dependency - ~6.3MB installed on a node without `rpicam-apps` already providing the shared `libav*` stack (PR #314 review caught CAM-0's original ~2.9MB estimate as measured on a node that already had it), still well under a size that would justify gating.

**PDEATHSIG is per-THREAD, not per-process (`man 2 prctl`)** - this caught out both `camera/usb_driver.py`'s ffmpeg spawning (PR #314 review) and `meshsrv/adapter_ipc_client.py`'s adapter respawn (`_spawn_locked()`, F15): the kernel delivers the death signal when the specific thread that called `fork()` exits, not when the whole parent process does. Calling `subprocess.Popen(preexec_fn=_set_pdeathsig_to_sigkill)` directly from a request-handling or other short-lived thread arms the signal against that thread's own lifetime - it "works" under gunicorn's gthread pool only because those worker threads happen to be long-lived, and silently kills the child the moment a short-lived spawning thread (a `python server.py` dev-server request, `_do_reconnect`, `_do_identity_retry`) returns. Fixed once, generally: `meshsrv/subprocess_spawner.py` is one process-wide, never-exiting spawner thread every PDEATHSIG-armed `subprocess.Popen()` call in this codebase now routes through (`spawn()` hands it a zero-argument `popen_fn`, blocks the short-lived calling thread until the real `Popen` object comes back) - both `camera/usb_driver.py` and `meshsrv/adapter_ipc_client.py` use this one shared implementation instead of each rolling its own. Any *future* caller of `preexec_fn=_set_pdeathsig_to_sigkill` from a thread that isn't guaranteed to outlive the child should route through this module too, rather than reintroducing the bug a third time.
- **Network (RTSP) camera sources (CAM2, Phase 1a - configuration only, no stream yet)**: `camera/source_store.py` `CameraSourceStore` keeps saved sources in instance-scoped `data/camera_sources.json` (no secrets) and the password in `data/camera_secrets.json` (mode 0600, NOT encrypted - a key next to the data would be obfuscation; write-only everywhere else, the API only says `password_set`). `camera/address_policy.py` is the SSRF guard (every resolved address must be RFC1918 / link-local / ULA; refuses loopback, the host's own addresses, cloud metadata and, in a container, the default gateway; callers connect to the validated IP, not the name, and re-validate on every connect). `camera/rtsp_input.py` builds the ffmpeg input so the password is never in argv: ffmpeg gets a secret-free argv and reads a two-line ffconcat script on stdin (`file '<url>'` then `option rtsp_transport tcp`, the option line MUST come after the file line). `camera/rtsp_driver.py` `RtspCameraDriver` is a `CameraDriver` whose `detect()`/`get_status()` do no network I/O; `CameraManager.replace_network_drivers()` syncs saved sources into the live manager (CSI/USB untouched), `build_camera_manager(network_drivers=...)` registers them even without local hardware. Routes: `api/api_camera_sources.py` (`/api/camera/sources`, rate limited; CSRF/auth from the global hooks). `tests/fixtures/fake_rtsp_server.py` is a stdlib fake camera (Basic auth) for tests that need a real ffmpeg. **Phase 1b (stream + UI)**: `camera/rtsp_stream.py` runs ONE ffmpeg per source (`-c copy`, no transcode, fragmented MP4 on a pipe) and fans it out: `FragmentRelay` keeps a bounded window of fragments, viewers are cursors into it (a slow client is moved to the newest keyframe, memory never grows), `ViewerLimiter` caps viewers at 4 per source / 6 total, `Backoff` retries 2 s ... 60 s with jitter and resets only after 20 s of stable stream. Failures a retry cannot fix (`auth_failed`, `stream_not_found`, H.265/non-H.264, `address_blocked`, `ffmpeg_missing`) are TERMINAL: no retry until the user edits the source or presses Reconnect (repeated bad logins can lock a camera account). The codec, resolution and fps come from the init segment / fragment headers (`camera/fmp4.py`), no ffprobe and no second RTSP session. The upstream starts on the first viewer and stops 60 s after the last (cold start measured 2.7 s median on a PC, 5-13 s on a Pi Zero 2W, dominated by the camera's keyframe interval; a warm join is immediate). Routes in `api/api_camera.py`: `GET /api/camera/stream/fmp4` (429 `viewer_limit`, 503 `stream_not_ready`), `POST /api/camera/stream/profile` and `/reconnect`. `camera/mjpeg_fallback.py` is the MJPEG path for browsers without MediaSource: a local ffmpeg fed from the SAME relay (never a second camera session), OFF on low-power hosts. A viewer with no data for 15 s is ended (a WSGI generator only notices a gone client when a write fails; without this a reloaded page leaks a slot while the camera is down), a stream route sets `SO_SNDTIMEO` + `TCP_USER_TIMEOUT` (30 s) on the client socket so a viewer whose network path died releases its slot, thread and upstream (found live: Send-Q 224 KB, rto 120 s), and every stream ends after 10 min so the player reconnects and is authorised again (login is a signed cookie, a logout cannot reach an open response). The stall watchdog is 15 s (a restart costs a 5-13 s cold start; 8 s restarted the stream about once a minute on a lossy Wi-Fi). The CSI-global routes (`/api/camera/switch_mode`, settings, stop, screenshot, mode) never touch the sensor while a network camera is active (opening the Camera tab used to start Picamera2). Frontend: `static/camera-ip.js` (MediaSource / ManagedMediaSource player with a 3 s live-edge target, reconnect, status polling; chat-camera.js delegates to `window.MCIpCamera` for network cameras) and `static/camera-sources.js` (add/edit/delete in the Devices tab, write-only password field, UI1 delete dialog). While a network camera is active the CSI/USB mode/image controls are hidden (Phase 3 adds the controls such a camera really has). **UX3 - the Camera card is one component for every source type**: the header (title left, source picker and power button right, one fixed picker width) and the tab row (`cameraControlTabCamera` Mode / `cameraControlTabImage` Image / `cameraControlTabLens` Lens, labels `camera.tab_*`) are template-owned and shared; `switchCameraControlTab()` (`static/chat-camera.js`) delegates to `MCIpControls.selectTab()` while a network camera is active (Image is hidden for it, Lens only with a zoom capability), so `camera-ip-controls.js` renders panels only. The stream picker (`#ipCameraProfile`) and Reconnect live in the IP Mode panel and are wired by delegated listeners in `camera-ip.js` (the panel is rebuilt when the source changes). The status line (`.camera-live-status`) sits at the right end of the tab bar for every type and drops under the tabs when the card is narrow. The picture box follows the picture's aspect ratio on every width (`--camera-aspect` / `--camera-ratio`, set by `setAspect()` and `showCameraFeed()`), no black bars. - `meshsrv/timer_service.py` - in-memory stopwatch/countdown timer state, session-scoped by design (resets on service restart). The countdown itself ticks client-side; this module only tracks elapsed-time bookkeeping (derived from a banked `accumulated_s` plus the current running segment, never accumulated tick-by-tick, to avoid drift) and runs the finish notify-pipeline when the frontend reports a timer reaching zero.
- `meshsrv/notification_service.py` - the in-memory notification queue backing the Notification Center card. Every source (Schedule Engine, timers, system events) pushes through one `push_notification()` entry point; resets on process restart, same lifetime as `time_service`'s status cache.
- `meshsrv/action_engine.py` - a lightweight, synchronous action registry/runner bridging interactive UI operations and backend handlers, one stable abstraction for current and future actions without changing the existing HTTP endpoint/UI contract. Stays synchronous deliberately - Node Tools already serialize access to the radio.
- `meshsrv/inbound_events.py` - the one Core-side ingest for received text, waypoints, NodeInfo, positions and telemetry, whichever transport delivered them: `ingest_received_text()` / `ingest_received_waypoint()` / `ingest_received_nodeinfo()` / `ingest_received_position()` / `ingest_received_telemetry()` each take a neutral event (`meshsrv/radio_transport.py`) and do what used to sit inline in `server.py`'s serial parsers (packet-id dedup, node update, text-fallback dedup, chat routing, reply reference, `add_message`, MCAttach dispatch, `WaypointStore.upsert` for text/waypoint; the NodeInfo/Position/Telemetry merge rules are shared with the serial parsers via `_merge_nodeinfo_into_node()` / `_merge_position_into_node()` / `_telemetry_values_from_metrics()` in `server.py`, so the two transports build state from one rule set instead of two copies that can drift). Serial builds the event from a CLI line (`build_serial_text_event()`, `process_waypoint_line()`, `process_nodeinfo()`); the TCP adapter's `drain_received()` supplies all five kinds. Safety gate: an event whose `local_radio_node_id` is not the active accepted radio (`active_radio_node_id()`) is dropped before anything is persisted. State is injected through `InboundDeps`, built per call by `server._inbound_deps()` (some of it, e.g. `seen_ids`, is rebound by background cleanup). `tests/test_serial_inbound_characterization.py` / `tests/test_serial_nodeinfo_telemetry_characterization.py` pin the serial behaviour; `tests/test_inbound_parity.py` pins that a serial line and the equivalent TCP packet leave identical state (Position has no serial counterpart, so it is unit-tested directly in `tests/test_inbound_events_nodeinfo_position_telemetry.py` instead).
- `meshsrv/inbound_worker.py` - the TCP inbound poller (`radio_inbound_worker` thread, started for every transport): `drain_received()` through the router about once a second, routes each event by type into `meshsrv/inbound_events.py`'s matching `ingest_received_*()`. Gated per tick by `server.inbound_eligibility()` (accepted transport is TCP AND identity `MATCH` AND the router is on TCP), so a live Settings switch needs no restart; `BUSY`/`NOT_CONNECTED`/reconnect are waited out silently, a bad event is dropped alone, message text is never logged. Counters are in `/api/radio_health` under `inbound`. A session torn down for a failed identity check also discards the adapter's captured queue (`teardown_unverified_tcp_session()`). Scope is text, waypoints, NodeInfo, positions and telemetry (routing ACKs and remote waypoint deletion are not received); see docs/BACKEND_API.md "TCP inbound worker".
- **Delivery ACKs (ST1)** - one rule, `server.resolve_pending_ack(request_id, error_reason, from_num)`, three sources: the serial `--listen` parser (`process_routing_ack_line`, now also reading the sender), TCP `ReceivedRoutingEvent`s (adapter subscribes to `meshtastic.receive.routing`, `inbound_events.ingest_received_routing`), and - serial only - the ACK **captured inside the send's own claim** (`adapters/meshtastic/_ack_support.py`'s `RoutingAckWaiter`, up to 12 s, returned as `SendResult.ack_state`). "Delivered" needs `from == the DM's destination`; a relay's "NONE" is an implicit ack and stays "sent"; any routing error is "unconfirmed". `ack_timeout_worker` runs for every transport; Bluetooth never stamps an ack deadline. While a DM's ACK is outstanding `TransportRouter.hold_background()` keeps background claims (channel read, time sync) off the radio. pubsub fixes a topic's signature at its first subscriber: both routing subscribers are `(packet, interface=None)`.
- **Router priority and budgets (ST1)** - `TransportRouter` gives sends priority over background claims (`get_channels`/`set_device_time`/`get_nodes` are BUSY while a send waits or during an ACK window) and refuses to start a call whose caller asked for >= 5 s but has < 5 s left after waiting for the lock (BUSY instead of a 0-1 s call that times out and kills the adapter). Channel discovery is single-flight with a 6 h TTL (re-read when `TransportRouter.connection_generation` changes - connect/reconnect/switch/serial path change - and on `?refresh_channels=force`; the UI's page-load `?refresh_channels=1` is a *soft* refresh honoured only when the cache is older than 10 min) and a 60 s failure backoff; the radio clock is synced once per connection (budget 40 s - the serial claim alone is ~10 s) and then every 6 h, never by the listener restart that ends a claim and never by a crash restart earlier than 6 h after the last attempt (a failed attempt retries after 30 min); the listener's exit counters are also journaled as `[LISTENER EXITS] ...` (on change, at most every 5 min) so they are readable without a login; a listener exit within 30 s of our own stop request is "intentional" (no ERROR) and `compute_radio_health_status(restarting_after_claim=True)` reports PAUSED, not LISTENER_DOWN. **Post-claim listener exits, root-caused (ST1, strace on dev):** a listener started right after a claim makes the firmware stream its config/NodeDB; on ESP32 USB-serial radios the firmware's text debug log can land inside a protobuf frame, the library fails that `FromRadio` parse (`Wire format was corrupt`), its reader thread dies and the CLI exits 1 after its own ~30 s connect timeout. `line_signals_corrupt_frame()` (`meshsrv/serial_reconnect.py`) makes `run_listener()` restart at once instead; counters `unexpected_exits` / `post_claim_listener_exits` / `frame_corrupt_restarts` are in `/api/radio_health` under `listener_exits`. The firmware-side cause is not fixable from Core.
- **Release radio (RR1)** - `RadioConnectionManager` (`meshsrv/radio_manager.py`) now serves serial AND TCP: `release(duration_s)` / `reconnect()` / `end_release()`, absolute `until`, `expired()` polled by `release_timer_worker` (every 5 s, all transports; calls `_auto_resume_released_radio`). TCP hooks: `_tcp_release_hook` (waits <=30 s for `tcp_link_lock`, then `tcp_ipc_transport.disconnect`), `_tcp_resume_hook` (`tcp_link_supervisor.trigger_now`). A TCP release is persisted by `meshsrv/radio_release_store.py` (`data/profiles/<id>/radio_release.json`); `start_runtime()` calls `_restore_persisted_tcp_release()` BEFORE the boot identity probe so a restart while released never dials (an expired record is deleted); a serial release is in-memory only. Everything that dials sees `is_released()`: the supervisor (`is_released=`; zero attempts, nothing counted, re-checked inside `_run_attempt`), `inbound_eligibility()`, `is_radio_available()` (sends/Node Tools/MCA/schedules fail fast with `radio_released`), `_probe_tcp_identity` + detect/accept routes (409 on the released endpoint). Explicit TCP connect/transport/reconnect and profile activation call `_end_tcp_release_for_explicit_connect()` (= the Reconnect, no second attempt). `tcp_ble_autorecovery` is read for Bluetooth only. Health: `RELEASED` is level `INFO` (neutral) for serial and TCP; `/api/radio_health` carries `released: {since, until, remaining_s, kind}`. Bluetooth is not releasable.
- `meshsrv/tcp_link_supervisor.py` - the ONE recovery path for a TCP radio link (DK2). **Contention (RR1)** is flagged from radio-side closes regardless of session length (>=3 in 5 min, >=4 in 10 min, or >=4 in 1 h at near-regular gaps), latched until a session has stayed up 15 min, delay floor 5 min (10 min after 30 min flagged); a single reboot/Wi-Fi blip/long power-off is one loss and never flags; it never releases the radio by itself. `TcpLinkSupervisor` (stdlib-only, everything injected, fake-clock testable) runs on its own thread (started in `start_runtime()` AFTER the boot transport restore) and, while the accepted radio is TCP and identity is not `MISMATCH`/`NOT_FOUND`, keeps trying forever: a 25 s hold-off after a lost link, then 30/60/90/120 s and every 120 s from there (+-10 % jitter), never giving up; a session counts as recovered after 20 s up. `server.tcp_link_attempt()` is the single attempt: close the old session first (the radio serves one client; the probe must never be a second one), `verify_radio_identity(retry=False)`, on `MATCH` `restore_active_transport()` reusing the probe connection - never any serial release / `lsof` / `/dev/tty*`. `POST /api/meshtastic/reconnect_now` (the Node Manager Reconnect button for TCP) is `trigger_now()`: reset backoff, attempt on the next tick; the endpoint comes from the accepted profile, not `settings.meshtastic`. One re-entrant `tcp_link_lock` serialises boot probe, supervisor and Reconnect. It replaces `process_identity_recovery()`/`process_transport_autorecovery()` for TCP (both stay for Bluetooth/direct callers; `radio_health_worker()` skips them for TCP). Health for TCP: `RECONNECTING` (amber, carries `reconnect:{state,attempt,next_in_s}`) while it works; a router not actually on TCP never reads CONNECTED; `packet_age` is informational only. Liveness is the transport's own: `adapters/meshtastic/tcp_transport.py` sets SO_KEEPALIVE (30/10/3) + `TCP_USER_TIMEOUT` (60 s) on the socket and **disables the Meshtastic library's own silent `_reconnect()`** (it re-dialled from the reader thread - a second client, a blocking `create_connection()`, and a reader thread that stayed alive so the link read CONNECTED for hours); a lost link now marks the interface dead at once. `TransportRouter.refresh_connection_info()` skips a serial IPC transport (a refresh would run the serial-port claim under the router lock - 8 s and `utility_missing` in a container - and a TCP profile whose router still sits on its serial default hit exactly that at boot).
- `meshsrv/installation_identity.py` / `meshsrv/installation_time_assignment.py` - a per-installation identifier (`MC1-XXXX-XXXX-XXXX-XXXX-XXXX`, pure entropy via `secrets.token_hex()`, no hardware/personal data folded in - see `PRIVACY.md`), stored in `data/instance.json`'s schema-v2 `installation` block (`meshsrv/instance_manager.py`). `installation_identity.py` generates/validates the ID and offers `get_confirmed_utc_time()` (gated on `time_service` reporting NTP-synchronized, lazily imported to keep this module's core two functions stdlib-only); `installation_time_assignment.py` runs a background thread that polls fast (15s, up to 5min) then slow (20min, indefinitely) until NTP is confirmed, then assigns `installation.assigned_at`/`time_source` exactly once and exits. `scripts/manage_installation_id.py` is the CLI for inspecting (`show`, genuinely read-only via `InstanceManager.peek()`) or regenerating it (`regenerate`, refuses outright while the service is active - no override - since `InstanceManager` caches in memory and a live process would silently keep serving the old ID).
- `modules/display/` - the optional e-Paper display subsystem (Waveshare 2.13" 4-color and WeAct 1.54" B/W panels). `manager.py`'s `DisplayManager` is the background worker turning `mark_dirty()` requests into actual debounced, hash-deduped panel refreshes (never blocks the caller - pending-state, not a frame queue), on its own thread matching `listen_meshtastic`/`telemetry_worker`'s pattern. `service.py`'s `epaper_worker()` polls MeshCenter's own already-collected in-memory state (nodes/radio/CPU/RAM) into `mark_dirty()` calls - never issuing its own `meshtastic --info`. `pages/` holds the six screens (status/radio/power/system/message/alert); `drivers/` holds the per-panel hardware implementations. `config_store.py` persists e-paper settings instance-scoped (`data/epaper_config.json`, not per-profile - the physical HAT belongs to the Pi, not a radio profile).

### Message display and "Reply with signal" (SIG1)

Every received text stores its own radio metrics as `msg["rx"]` (`snr`, `rssi`, `hop_start`, `hop_limit`; only real finite numbers, no key when there is none): `inbound_events.ingest_received_text()` passes them to `add_message(rx=...)` for serial (the `--listen` line's `rxSnr`/`rxRssi`/`hopStart`/`hopLimit`) and TCP alike. `MCViews` (`static/chat-views.js`) owns the pure logic: `buildSignalReplyText()` (language-neutral, real newlines, ASCII only, no names), `signalReplyMenuState()` (hidden for own/system messages, without SNR/RSSI or without a packet id; disabled while the radio is released) and the display helpers `expandEscapedNewlines()` (a literal backslash-n / backslash-r backslash-n becomes a real line break at DISPLAY time only; callers escape the result, nothing builds HTML from message text) and `previewText()` (one-line previews use " · "). **SIG2:** the display conversion exists for messages stored BEFORE the fix - the root cause was the serial parser: `extract_text_message()` used to store the Python repr of the `--listen` line verbatim (a real newline became backslash-n, a real backslash two backslashes). It now decodes the string literal (a strict `ast.literal_eval` of one verified token, `_python_string_literal_at()`; the packet's own `payload` bytes are skipped; malformed escapes fall back to the raw text and log once) and does not strip, so serial stores byte for byte what the TCP adapter stores (`tests/test_serial_text_decoding.py`). `build_serial_text_event()` reads the sender, channel, packet id and radio metrics from `line_without_text_literals(line)`, so a text containing `'fromId': '!...'` cannot forge them. Known edge: a user-typed literal backslash-n still displays as a line break. The same repr problem exists for waypoint names/descriptions and NodeInfo names (not changed). The menu item sends through `submitOutgoingMessage()` with `buildReplyPayload()`, the same native-reply path as Reply.

### Form preferences

Reusable, non-content preferences in composer-style forms (checkboxes, notify/mesh toggles, target type, selected channel/node) are persisted server-side, not to `localStorage`: `appSettings.<section>` round-trips through `GET`/`POST /api/settings`, with `normalize_settings()` in `api/api_settings.py` as the source of truth for each section's shape and defaults (`DEFAULT_SETTINGS`). Where a preference should differ per connected radio, the section carries a `profile_defaults` map keyed by the active radio profile ID (lowercased, `[a-z0-9_-]{1,64}`) fetched from `/api/base_status`, with the section's top-level fields as the global/legacy fallback. Content fields (name, description, message text, coordinates, duration) are never remembered - only structural/preference choices are. Reference implementation: the Waypoint creation form's `getWaypointComposerDefaults()` / `saveWaypointComposerDefaults()` / `loadWaypointComposerContext()` (`static/chat.js`, around `openCreateWaypointDialog()`), backed by the `waypoints` settings section. The Timer form (`static/chat.js`, `openTimerForm()`) follows the same pattern via a `timers` settings section and `getTimerComposerDefaults()` / `saveTimerComposerDefaults()` / `loadTimerComposerContext()`, restoring on form open and persisting on each relevant field's `change` event rather than only at submit (Stage 8 addendum, `feature/time-system`).

### Internationalization (i18n)

UI strings go through a hand-rolled runtime, `static/i18n.js` (`window.I18N.t()` / `.plural()` / `.applyStaticDom()`), backed by one JSON catalog per locale under `static/i18n/{en,de,ru,uk}.json`. New user-facing strings must use `I18N.t()` (or `data-i18n*` attributes in static markup) instead of hardcoded English, added to all four catalogs in the same commit. See `static/i18n/CONVENTIONS.md` for the short rulebook (tone per locale, key-naming, plural handling) and `static/i18n/README.md` for the do-not-translate glossary (Meshtastic, Waypoint, GPS, etc.) and the reasoning behind ambiguous cases. Translation coverage is uneven - check the README's "Localization" section before claiming a UI area is fully translated.

### REST API

Routes are split between `server.py` (nodes, chats, waypoints, telemetry, system, radio profile/connection management) and `api/api_*.py` (camera, chat send worker, settings, system actions, node tools, node icons, weather). See the README's "REST API" section for the representative endpoint list; the JS in `static/*.js` is the actual client.

## Writing style

**No em dash and no en dash, anywhere.** In docs, release notes, README, CLAUDE.md, UI strings (the `static/i18n/*.json` catalogs, templates, JS), server and log messages, installer output and code comments, use a plain hyphen-minus (` - ` for a sentence dash, `5-20` for a range, `-` as an empty-value placeholder). `scripts/check_no_long_dashes.py` (a CI step, also run by `tests/test_no_long_dashes.py`) fails on U+2014 and U+2013 in every tracked text file with file:line; its allowlist is limited to licence texts (`LICENSE*`, `licenses/`), vendored/minified bundles, `tests/fixtures/` (real CLI/radio output) and the one data line in `tests/test_mime_allowlist.py`. Add to the allowlist only for genuine data, with the reason in the PR. Keep this rule in mind for text you generate (release notes, i18n values in all four languages): check it before committing.

## Repository guard (no archives, no big files)

`scripts/check_no_large_files.py` rejects any tracked file over 5 MB and any `*.tar`, `*.tar.gz`, `*.tgz` (a CI step and `tests/test_no_large_files.py`). Why: a locally built Docker image archive (it contains GPLv3 code, images are never published) was once committed with `git add -A` and pushed to the public repository. CI only runs on pull requests, so the real prevention is local: `scripts/git-hooks/pre-commit` (staged files) and `pre-push` (commits being pushed). Switch them on once per clone with `git config core.hooksPath scripts/git-hooks` (shared by every worktree of the clone). Stage files by explicit path, never `git add -A`, and keep build output (image archives, release bundles) outside the repository.

## Deployment

`deploy/meshcenter.service` is a template (`__MESH_USER__` / `__MESH_HOME__` placeholders filled via `sed` at install time, see INSTALL.md) for running under systemd. As of PR #69, its `ExecStart` runs `gunicorn -c gunicorn.conf.py wsgi:app`, not `python server.py` directly - production is a real WSGI server now, not Flask's Werkzeug dev server. `wsgi.py` does `from server import app, start_runtime` and calls `start_runtime()` explicitly at import time, since a WSGI server never executes `server.py`'s own `if __name__ == "__main__":` block.

`gunicorn.conf.py` (repo root, loaded automatically by `-c` + `WorkingDirectory`) hardcodes `workers = 1` - not a performance choice, a correctness requirement. The radio listener owns the serial port exclusively and all runtime state (`nodes`/`chats`/`messages`/`settings`) lives in one process's memory behind `state_lock`; a second worker process would run its own `start_runtime()` and race the first for the same serial port. `start_runtime()` also takes an OS-level `flock()` on `data/runtime.lock` (`_acquire_runtime_lock()` in `server.py`) as a second, independent guard in case `workers` is ever overridden - a second process fails loudly (`[FATAL] ...`) instead of silently corrupting state. `worker_class = "gthread"` (not the `sync` default) is what lets `/video_feed`'s long-lived MJPEG stream coexist with ordinary API traffic instead of blocking the whole process for whoever's watching the camera.

Rollback to the old direct-run command is a one-line `ExecStart` edit, documented in `deploy/meshcenter.service` itself; `python server.py` still works exactly as before for local/manual runs, `start_runtime()`/`app.run()` unchanged.

`deploy/meshcenter.sudoers` and `deploy/meshcenter-wifi.sudoers` grant the narrowly-scoped sudo rules needed for the in-app system actions (restart/reboot/shutdown) and Wi-Fi management (NetworkManager) respectively - extend these rather than widening sudo access when adding new privileged actions.

### Docker / container mode (DK1)

`Dockerfile` + `deploy/docker/` build a single-container, TCP-only, `linux/amd64` image (Core + adapter, two venvs, one container; see `docs/Docker_Installation.md`). `meshsrv/runtime_env.py` is the one switch: `MESHCENTER_RUNTIME=container` (exact value, no heuristics) turns off host-only capabilities (reboot/poweroff, Wi-Fi/network, self-update, hardware config, host-identity metrics) with a 403 `not_available_in_container` refusal and a UI notice (`static/runtime-caps.js`); with the variable absent every code path is the native one, unchanged (tests/test_docker_support.py pins both). Restart in container mode is a SIGTERM to the gunicorn worker (the master respawns it), not `systemctl`. `/healthz` is unauthenticated, GET-only and returns only `{"status":"ok"}`. Config comes from `/config` (a `.pth` file in the Core venv only - never `PYTHONPATH`, which would leak into the adapter), data from `MESHCENTER_DATA_DIR`. A prebuilt image would redistribute GPLv3 code - build locally only until the D0 section 5 gap is closed.

### Testing unmerged code on a live node: full branch checkout only, never individual files

Never `scp`/copy individual changed files onto a node's tracked checkout to live-test a branch, even for a quick check. A file pulled from a newer branch can depend on other files (new modules, changed signatures) that the node's current commit doesn't have - the failure mode is an import-time crash, not a clean rejection, and a node running its own out-of-band work (an unpushed local branch, local merge commits never pushed anywhere) makes this easy to get wrong without noticing until a restart. This happened live: copying only `camera/usb_driver.py` + two `meshsrv/` files from `fix/f15-shared-subprocess-spawner` onto pixel-111 (at the time running an unpushed `feat/tcp-probe-separation` branch, since reset to a clean `main`) crash-looped gunicorn, because that node's checkout predated CAM-1 (#314) and never had `camera/v4l2_ctl_parse.py`, which the new `usb_driver.py` imports at module load.

Instead: record the node's current branch/commit (`git branch --show-current`, `git rev-parse HEAD`) and confirm `git status --short` is clean first; `git fetch origin && git checkout <branch-or-PR-head>` to test the real, complete tree; then `git checkout <original-branch-or-commit>` to restore exactly, and restart the service. If the node has unpushed local commits (check `git log origin/<branch>..HEAD`), checking out something else is still safe - the commits aren't lost, just not checked out - but confirm you can get back to the exact original commit before switching away from it.
