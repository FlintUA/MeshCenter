# Handoff: Step 0.2 (крипто-ADR + проверка на Pi) — для сессии с доступом к `dev`/`prod`

Эта заметка — не ADR. Это задание для другой Claude Code сессии («code»), у которой
есть доступ к аппаратным нодам (`dev` 192.168.2.104, `prod` 192.168.2.103, обе —
Pi Zero 2 W), в отличие от текущей Cowork-сессии, у которой есть только device
bridge к Windows-машине `minipc` (репозиторий смонтирован в
`C:\Users\Flint123\projects\MeshCenter\`, но сами Pi не подключены).

Файл можно удалить после того, как `docs/architecture/ADR-0002-crypto-suite.md`
будет создан и подтверждён — тогда он выполнил свою роль.

## Контекст

Из плана (`MCAttach_Execution_Plan.md`, Шаг 0.2) и спецификации (раздел 7.3, 8.1-8.2):

- `suite_id = 1`: Ed25519 (подписи), X25519/Curve25519 sealed box (упаковка ключа
  получателю), XChaCha20-Poly1305 (шифрование манифеста и чанков), SHA-256 (digest),
  HKDF-SHA-256 (разделение производных ключей).
- Решение, принятое на уровне плана, но **не подтверждённое на реальном железе**:
  X25519-ключ получателя выводится из объявленного Ed25519 identity штатной функцией
  libsodium (`crypto_sign_ed25519_pk_to_curve25519`), а не хранится как отдельный
  ключ. Это держит `KEY_ANNOUNCE` в одном text-frame (~156 байт). Спецификация сама
  оценивает уверенность в этом решении как **среднюю до крипто-ADR и теста
  библиотечного API на целевом Pi** (раздел 7.3).
- Domain-separation labels для pointer signature и descriptor signature должны быть
  **разными** (спецификация, раздел 8.2, п.10-12) — это тоже часть ADR-0002, не
  только конверсия ключа.

Этот шаг блокирует Step 1.2 (MCA principal + Meshtastic address binding) текущего
плана: до подтверждённого ADR-0002 сгенерированный X25519-ключ в MCA principal не
может считаться финальным форматом.

## Что нужно сделать

1. Установить PyNaCl (или другой проверенный libsodium-биндинг) в **Core venv**
   на `dev` и на `prod` — именно в Core venv, не в `adapters/meshtastic/venv`,
   поскольку крипто-логика целиком принадлежит MIT Core.
2. Написать `tests/crypto/test_key_derivation.py`: round-trip Ed25519→X25519
   против фиксированного test vector (детерминированность — одинаковый
   Ed25519 keypair должен давать одинаковый X25519 pubkey на обеих машинах).
3. Написать `tests/crypto/test_bench.py` (помечен как benchmark, не гейтит CI,
   но обязателен к ручному прогону на обеих Pi перед закрытием шага):
   - `crypto_sign_ed25519_pk_to_curve25519` — время конверсии;
   - генерация Ed25519 keypair — время;
   - XChaCha20-Poly1305 шифрование одного 256 KiB чанка — время и peak RSS.
4. Написать `docs/architecture/ADR-0002-crypto-suite.md`:
   - зафиксировать выбор конверсии Ed25519→X25519 (или откат — см. ниже) с
     реальными числами замеров на dev и prod, а не «быстро/медленно»;
   - зафиксировать domain-separation labels для pointer signature и descriptor
     signature (разные строки, раздел 8.2 п.10-12);
   - явно указать: время шифрования одного 256 KiB чанка укладывается ли в
     бюджет, при котором файл 5 MiB (20 чанков) шифруется за разумные единицы
     секунд на Pi Zero 2 W — это единственная измеримая метрика, нужная
     позже в Шаге 1.9 для performance budget.

## DoD

- Конверсия работает и даёт совпадающий результат на `dev` и `prod`.
- Замеренное время шифрования зафиксировано числом в ADR-0002 (не оценкой).
- `ADR-0002-crypto-suite.md` существует и подтверждён.

## Если конверсия не работает на целевой платформе

Откат к варианту с двумя независимыми ключами (спецификация, раздел 27, п.2):
X25519-ключ рассылается отдельным полем/frame, а не выводится из Ed25519.
Это меняет формат `KEY_ANNOUNCE` (два frame вместо одного, см. раздел 7.3
последний абзац и раздел 7.5 про `KEY_ROTATE`) и требует частично переписать
Шаг 0.1 (ADR-0001, байтовый бюджет `KEY_ANNOUNCE`) и Шаг 0.4 (codec). Явно
зафиксировать этот риск в ADR-0002, если он реализовался — не откладывать.
