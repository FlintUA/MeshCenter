# Docker blockers and GPL-compliant adapter distribution blockers (D0)

**Status:** read-only audit, no behavior changed. No Dockerfiles, Compose files, or TCP implementation exist as a result of this document — per the D0 brief, that's explicitly out of scope. This is a blocker inventory to inform D1-D9 sequencing.

Built against `origin/main` @ `2adf32a`, via a full-repo grep sweep (excluding `relay-server/`, `static/`, `tests/`) for every category the D0 brief named, each hit verified by reading surrounding context.

---

## 1. What currently prevents starting without a serial device

| Blocker | Where | Severity |
|---|---|---|
| `resolve_meshtastic_cli()` raises `SystemExit(1)` if the CLI binary can't be found anywhere on its 5-step search path | `server.py:203-209`, `meshsrv/runtime_identity.py` | **Hard blocker for `import server`** — even before a serial port is checked. A Core container with no adapter venv/CLI binary anywhere on the resolvable path cannot import `server.py` at all, let alone run without a radio. |
| A missing/unplugged serial port is handled gracefully | `server.py:211-252` | **Not a blocker** — `resolve_serial_port()` degrades to a printed warning; `server.py` already documents this was a deliberate fix (Task 47) for exactly "no radio attached" not crashing the whole process. Confirms Core *can* start with no physical radio, once the CLI-binary check (above) passes. |
| `verify_radio_identity()` probes the radio once at `start_runtime()`; `identity_match=False` gates the listener + 6 of the 12 background threads off, but does not stop the app from serving HTTP | `server.py:5972-6129` | Not a blocker — already the "degraded state" path the codebase explicitly designs for. |
| `_acquire_runtime_lock()` skips silently (with a log line) if `fcntl` is unavailable | `server.py:5920-5928` | Not a blocker for Linux containers; only relevant to non-POSIX dev environments. |

**Conclusion:** starting Core without a serial device physically attached already works today (that's the existing "degraded state" design). Starting Core without the Meshtastic **CLI binary resolvable at all** does not — this is the actual, single point where a bare "Core-only, no adapter" container image would fail at `import server` time, not at radio-connect time.

## 2. What currently prevents starting without systemd

This is the largest and most pervasive assumption in the codebase — see `dependency-map.md` §3.6 for the full grep hit list. Summarized as blockers:

1. **Orphan-adapter protection loses one of its two legs.** `deploy/meshcenter.service`'s `KillMode=control-group` (systemd's default, live-confirmed via `systemctl show -p KillMode`, not assumed) is what makes a normal `systemctl restart`/`stop` **and** the `Restart=on-failure` auto-restart path also kill the adapter subprocess. This protection **does not exist** outside systemd — `meshsrv/adapter_ipc_client.py`'s own module docstring says so explicitly. The fallback, `PR_SET_PDEATHSIG` (Linux `preexec_fn`, Core→adapter parent-death signal), is the *only* remaining protection without systemd — and it only covers "the literal parent process died," which is exactly the property a cross-container split also breaks (see `ipc-carrier-audit.md` §4). **A containerized Core with no systemd equivalent (no `KillMode=control-group`) is already down to one layer of orphan protection even before any container-split is considered.**
2. **No self-restart target.** Three separate call sites shell out to `sudo -n /usr/bin/systemctl restart meshcenter.service`: `server.py:4950-4951` (after a radio-profile switch), `api/api_updates.py:19-21` (after a self-update), `api/api_system.py:30-32` (the UI's "Restart" system action). None of these have any fallback if `systemctl` doesn't exist — the restart simply fails (caught, logged as an error, but the app never actually restarts).
3. **`reboot`/`poweroff` UI actions** (`api/api_system.py`) are host-level operations with no meaningful container equivalent — a container "rebooting" or "powering off" itself is either meaningless or (if honored literally) would just kill the container with no host-level effect, silently changing the feature's actual behavior from what the UI promises.
4. **Logging format assumes journald.** `wsgi.py:17` and `gunicorn.conf.py` both note that their log format omits timestamp/PID specifically because systemd's journald normally adds that structure — a container log driver (Docker's default `json-file`, or most others) does not, so logs would silently lose that context unless the format string is adjusted for a non-journald destination.
5. **`scripts/manage_installation_id.py`** gates installation-ID regeneration on `systemctl is-active meshcenter.service` — this specific script is operational tooling, not runtime-critical, but would need adaptation if the deployment model changes.

## 3. What currently prevents starting without Raspberry Pi hardware

Distinct from "without a serial device" — this is about assumptions baked in even when no radio/camera/display operation is ever attempted:

1. **`camera/camera.py` creates `data/` and `data/screenshots/` unconditionally at import time** (`os.makedirs`, lines 47-48) — confirmed a real side effect of merely `import camera.camera`, which `server.py` does unconditionally at its own import time. Not Pi-specific by itself, but it means the camera module always touches the filesystem regardless of whether a camera is present or wanted.
2. **`libcamera`/`Picamera2` import risk** — handled defensively (see `dependency-map.md` §1.4) but still means Core's Python environment needs `--system-site-packages` visibility into the Pi OS's camera stack (`apt`-installed `python3-picamera2`) for the *possibility* of camera support to import cleanly, even on a build with no camera attached. This is a **build-time**, not run-time, blocker: a minimal `python:3.11-slim`-style container image cannot satisfy it without also installing the Raspberry Pi OS camera stack at the OS layer, which argues Core's image needs to be built `FROM` a Raspberry Pi OS-derived base or equivalent, not a generic Python base image.
3. **GPIO/SPI (e-Paper) hardware access needs `gpiozero`+`spidev`** (`modules/display/drivers/*`), and while none of that touches hardware at import time (confirmed clean in `dependency-map.md` §2), **actually using** the display feature needs either `--privileged` or specific `/dev/gpiomem`+`/dev/spidev*` device passthrough plus appropriate group membership inside the container — this is already optional/off-by-default (`EPAPER_ENABLED`), making it a good first candidate to exclude from a base "Core" image.
4. **I2C/RTC hardware access needs `/dev/i2c-N`/`/dev/rtc0` device passthrough** — but since all access goes through CLI tools (`i2cdetect`/`i2cget`/`i2ctransfer`/`hwclock`) rather than a Python bus library, this at least doesn't require anything beyond device-node passthrough + the relevant `i2c-tools`/`util-linux` packages in the image.
5. **`hardware/hardware_config.py`'s privileged helper edits `/boot/firmware/config.txt` and `/etc/modules`** — genuinely host-firmware-level changes needing a physical reboot to take effect. This is **not something a container can do at all** without host `/boot` and `/etc/modules` bind-mounted plus reboot access to the host, effectively requiring the container to run privileged/host-mode for this one feature specifically. This is the single clearest "must stay on the host, never move into any container" boundary found in this audit.
6. **`os.uname().nodename`/`platform.node()`** report container-internal values, not the physical Pi's hostname, once containerized — not a blocker to starting, but a behavior/UI-meaning change worth flagging.

## 4. What currently prevents running as two separate containers

This is the combination of every other finding in this audit, brought together:

1. **No carrier exists today for Core↔adapter communication other than a local OS pipe to a directly-spawned child process.** `meshsrv/adapter_ipc_client.py:349`'s `subprocess.Popen(..., stdin=PIPE, stdout=PIPE)` assumes both processes share a filesystem/process-tree/cgroup on one host. See `ipc-carrier-audit.md` for the full candidate-carrier evaluation (recommendation: Unix domain socket over a shared volume) — but regardless of carrier, **Core's direct ownership of the adapter's OS process (`proc.kill()`, `proc.wait()`) has no cross-container equivalent** and needs its own new design (an explicit shutdown/restart IPC operation, or reliance on the container orchestrator's restart policy).
2. **The two-legged orphan-adapter protection (§2.1 above) is entirely process-tree/cgroup-based** and has zero meaning across a container boundary — needs a replacement (most plausibly a container-runtime health check + restart policy on the adapter side, plus the adapter itself detecting it's been orphaned to run its own `bluetoothctl disconnect` cleanup, since Core can no longer reach it after the fact).
3. **`--system-site-packages` venv layout is not a "two `pip install -r requirements.txt` images" split.** Core's own venv needs `--system-site-packages` specifically to see `apt`-installed Picamera2/libcamera bindings — meaning even splitting Core and the adapter into separate images doesn't give Core a clean minimal-Python-base-image story; it still needs the Pi OS camera stack installed at the OS layer if camera support is to be included in that image at all.
4. **`config.py` has no absolute-path or env-var resolution** (`dependency-map.md` §1's headline finding #5) — both containers need `config.py` (or whatever replaces it) placed at a fixed `WORKDIR`-relative location via bind-mount/volume, since there is no `CONFIG_PATH` env var to point at an externally-mounted secret file instead. This is a real prerequisite gap for clean per-container secret injection.
5. **Single-instance design (`workers = 1`, `fcntl.flock()`) caps Core at exactly one replica, permanently, regardless of container topology** — not itself a blocker to a *two-container* (Core + adapter) split, since that's still "one Core, one adapter," but it rules out any future horizontal-scaling story for Core specifically, and is worth stating explicitly so D5+ doesn't accidentally design toward a multi-replica Core.
6. **BLE cleanup ownership splits awkwardly across a Core/adapter container boundary** (`dependency-map.md` §3.8) — both `adapters/meshtastic/ble_transport.py` and `meshsrv/adapter_ipc_client.py` independently run `bluetoothctl disconnect` against the same BlueZ session today; only whichever container retains BlueZ/D-Bus access post-split can actually perform this cleanup, so Core's own call site would need to be removed or turned into an RPC to the adapter side.
7. **Wi-Fi/NetworkManager management (`meshsrv/network_config.py`) needs host network-namespace/D-Bus access** (`nmcli`) — this doesn't block a Core/adapter split (it's orthogonal to the radio-adapter boundary), but it's a *third* container-hostile feature (alongside e-Paper GPIO and the hardware-config `/boot` editor) that would need `--net=host` or a privileged NetworkManager-D-Bus-proxy sidecar if ever containerized, worth tracking alongside the other two as a set of "host-privileged sidecar or leave on bare metal" decisions rather than solving each ad hoc.

## 5. GPL-compliant adapter distribution blockers

**What's documented today** (`THIRD_PARTY_NOTICES.md`, `adapters/meshtastic/LICENSE`, `pyproject.toml`, `adapters/meshtastic/requirements.txt`, `adapters/meshtastic/ipc_server.py`'s own docstring): a three-legged isolation model —

1. **Package/venv separation**: `meshtastic` (GPLv3) and its dependency closure live only in `adapters/meshtastic/venv`, never Core's own `venv/`. `pyproject.toml` structurally (not just descriptively) prevents `pip install .` from accidentally producing a wheel spanning both trees — flat-layout auto-discovery refuses to build without an explicit `packages=[...]` allowlist, which the project deliberately doesn't provide.
2. **Process separation**: `meshtastic` is imported only inside the adapter subprocess, reached exclusively via newline-delimited JSON on stdin/stdout — never a Python import across the boundary. The adapter's own docstring is explicit that the authors consider **process separation**, not merely venv/package separation, to be what does the actual legal work (their own stated FSF "mere aggregation" reasoning for separately-invoked programs communicating over a data channel, not a shared-address-space/library-call boundary).
3. **CI-verified non-importability**: `scripts/_smoke_test_core_harness.py` is a live, executed check (not just a documentation claim) that a Core-only extracted artifact cannot `import adapters`/`meshtastic` at all.

### The specific question this audit was asked to answer: does a single combined Docker image (both venvs, still two OS processes inside one container) satisfy this model?

**Reading of the existing documentation's own stated reasoning:** yes, as currently architected and reasoned about — because the authors' own comment (`adapters/meshtastic/ipc_server.py`, quoted directly: "venv separation isolates dependencies, not [licensing status]") frames **process separation as the operative boundary**, and nothing in `THIRD_PARTY_NOTICES.md` or `pyproject.toml` claims the two venvs must additionally live in separate deployable artifacts. The existing bare-metal Pi install already puts both venvs on the same host filesystem — architecturally the same shape as "same container, two venvs, two OS processes." A single combined image that (a) keeps the two venvs as genuinely separate Python environments, (b) keeps `meshtastic` importable only from within the adapter's own interpreter invocation, and (c) preserves the stdin/stdout (or its future UDS/TCP replacement) JSON IPC boundary rather than a Python import, is a direct container-image analogue of the current deployment, not a weakening of it.

### What *would* be a genuine regression or new risk, not currently addressed by any documentation

1. **Redistribution posture changes.** Today, `install.sh` fetches `meshtastic` from PyPI onto the **end user's own machine** at install time — the project itself never ships GPLv3 code in a binary artifact. **Distributing a prebuilt Docker image with `adapters/meshtastic/venv` baked in changes this**: the project would now be redistributing GPLv3 code (plus its full dependency closure) inside something it ships, which is a materially different posture that likely triggers GPLv3's own redistribution obligations (source availability, license-notice inclusion alongside the distributed artifact) more directly than a "the installer pip-installs it for you" flow. **No current documentation addresses image-redistribution obligations at all** — the existing GPL section is written entirely from the "isolate at runtime on a machine that separately `pip install`s things" perspective. This is a genuine documentation gap, not an architectural one, but it's a real blocker to shipping a prebuilt combined (or even adapter-only) image without first closing it.
2. **No automated enforcement for a combined-image build path.** `pyproject.toml`'s flat-layout safety net (item 1 above) only protects a `pip install .` wheel build — it says nothing about a hand-written Dockerfile that `COPY`s both trees into one image and `pip install`s both requirement files. Docker doesn't care about setuptools' packaging guard. `scripts/_smoke_test_core_harness.py` only tests a **Core-only extracted archive**, not a combined-image build — there is currently no CI-equivalent check that a combined image keeps the two venvs/import-boundaries separate. Building such a check (a container-level analogue of the existing archive-based smoke test) is a concrete, actionable D5+ prerequisite, not just a documentation fix.
3. **If the adapter and Core end up in genuinely separate images** (the more architecturally clean option, and the one this audit's other findings — `ipc-carrier-audit.md`'s carrier recommendation, the orphan-protection redesign needed either way — already push toward), the redistribution-posture question in item 1 applies to the **adapter-only image** specifically, and is arguably easier to reason about (it's already a natural, separately-versioned artifact) but still needs the same documentation closure.

### Recommendation

Treat the **GPL documentation gap** (item 1 above) as a D5-adjacent prerequisite regardless of which carrier/container topology is chosen — it blocks *any* distributed image containing the adapter venv, combined or separate, and is independent of the carrier decision in `ipc-carrier-audit.md`. Treat the **missing combined-image CI check** (item 2) as a concrete, low-effort D5 deliverable once a container topology is chosen, mirroring the existing archive-based smoke test's enforcement style rather than relying on documentation/discipline alone.
