# MCAttach: File Transfer - Technical Reference

**Status:** Living document, current as of the ADR-0009 v2 inbound-ACK routing work (`mcattach-adr-0009-inbound-ack-routing`).
**Audience:** developers working on this codebase. For a non-technical explanation, see `MCAttach_File_Transfer_Plain_Language.md`. For multi-Relay specifics, see `MCAttach_Multi_Relay_Requirements.md`.
**References:** ADR-0001 (wire protocol), ADR-0003 (SQLite exception for MCA state), ADR-0005 (Relay identity), ADR-0006 (sender state machine), ADR-0007 (receiver state machine), ADR-0008 (backend layer, plus its PR #231 amendment), ADR-0009 (signed inbound control messages — ACK routing, superseding the earlier PR #231 exclusions).

## 1. What MCAttach is

MCAttach ("Meshtastic-Carried Attachments") lets two MeshCenter instances exchange files larger than a LoRa text message can carry, using a third-party **Relay** (an HTTPS object store, external to the mesh) to hold the encrypted file while the mesh itself only ever carries small, signed control messages describing where to find it and how to decrypt it. The mesh never carries file bytes; the Relay never sees plaintext or the decryption key.

Every MeshCenter instance has exactly one **MCA principal** per workspace (an Ed25519 signing keypair plus an X25519-derived encryption keypair, `meshsrv/attachments/identity.py`) - not tied to a specific radio profile, since the principal must survive a radio-profile swap. Trust between two principals is established via **TOFU** (trust-on-first-use): the first time a principal's public key is seen at a given transport address, it is recorded as a pending binding; a human explicitly confirms it before it becomes usable for sending.

## 2. Wire protocol (ADR-0001) - message types this codebase actually implements

All MCA/1 messages are CBOR-encoded, either inlined as Base64URL text prefixed `MCA1:` (`MCA1-TEXT`, used over Meshtastic - `meshsrv/attachments/delivery/meshtastic.py`) or as raw CBOR bytes (`MCA1-CBOR`, for a binary-channel transport). `meshsrv/attachments/codec.py` is the single place that encodes/decodes/verifies every message type:

| Code | Type | Purpose |
|---|---|---|
| 1 | `OFFER` | Sender announces a new attachment: `provider_id`, `transfer_id`, `sender_key_id`, size bucket, expiry. |
| 2 | `ACK_RECEIVED` | Receiver confirms it received and stored the OFFER (the sender's `SENT → RECEIVED` transition) - **not** that the ciphertext or plaintext was downloaded. |
| 3 | `ACK_DOWNLOADED` | Receiver confirms it decrypted and made the file available. |
| 4 | `ACK_PROVIDER_UNKNOWN` | Receiver reports it cannot resolve the OFFER's `provider_id`. |
| 5 | `CANCEL` | Sender withdraws an in-flight offer. |
| 6 | `KEY_REQUEST` | Requests the other side's current public identity. |
| 7 | `KEY_ANNOUNCE` | Announces a principal's public identity (signed). |
| 8 | `KEY_ACK` | Confirms receipt of a `KEY_ANNOUNCE`. |
| 9 | `REJECTED` | Receiver declined an offer. |
| 10 | `EXPIRED` | An offer's hard expiry passed before completion. |
| 11 | `KEY_ROTATE` | Announces a principal's key rotation. |

**Implemented today:** `OFFER`, `KEY_REQUEST`, `KEY_ANNOUNCE`, `KEY_ACK`, and — as of ADR-0009 v2 — the three sender-side simple ACKs `ACK_RECEIVED`/`ACK_DOWNLOADED`/`ACK_PROVIDER_UNKNOWN`. The ACKs are dispatched by `AttachmentsService._process_inbound_ack()` (worker thread, single owner of `conn`): each is decode-verified against the recipient public identity pinned on the exact transfer (`attachment_recipients.recipient_public_identity`, never the current TOFU binding), source-route-checked against the persisted DIRECT delivery row, then applied via `sender.apply_ack()` (see §3). `ACK_RECEIVED` advances `SENT → RECEIVED`; `ACK_DOWNLOADED` advances `SENT/RECEIVED → DOWNLOADED` and drops the transient `mca_sender_state` while retaining the `mca_sender_revoke_state` revoke capability; `ACK_PROVIDER_UNKNOWN` sets `error_code = recipient_provider_unknown` and is **non-terminal** (the attachment stays `SENT`, recoverable once the recipient's provider is corrected). `ACK_RECEIVED` is emitted the moment `handle_offer()` stores the OFFER (receiver.py, before any download), so it attests to *offer receipt*, never to ciphertext/plaintext delivery — the table above was corrected to match the code. **Not implemented** (flagged, not silently missing): `CANCEL`/`REJECTED`/`EXPIRED`/`KEY_ROTATE` still have no inbound dispatch path — those remain explicitly out of scope.

## 3. State machines

### Sender (`meshsrv/attachments/sender.py`, ADR-0006, ADR-0009)

```
DRAFT -> VALIDATING -> ENCRYPTING -> QUEUED_UPLOAD -> UPLOADING -> READY_TO_SEND -> SENT -> RECEIVED -> DOWNLOADED
                                                                      (terminal: FAILED_VALIDATION / FAILED_UPLOAD / FAILED_RADIO)
                                                                      (terminal: EXPIRED / REVOKED / CANCELLED)
```

`AUTOMATIC_STATES = {DRAFT, VALIDATING, ENCRYPTING, QUEUED_UPLOAD, UPLOADING, READY_TO_SEND}` - every non-terminal, non-`SENT` state `AttachmentsService`'s tick scan advances automatically via `run_step()`. `SENT`/`RECEIVED` are deliberately **excluded** from the automatic scan: they advance only off a verified inbound ACK via `sender.apply_ack()` (ADR-0009, §2), never off the tick. `create_draft()` records the recipient key_id(s) **and pins the recipient's exact 32-byte Ed25519 public identity** (`attachment_recipients.recipient_public_identity`) plus the delivery route (adapter/connector/route type/route id) at creation time; nothing after that call changes which Relay, which route, or which key an attachment's ACK is verified against.

### Receiver (`meshsrv/attachments/receiver.py`, ADR-0007)

```
WAITING_KEY -> WAITING_PROVIDER -> WAITING_NETWORK -> WAITING_CONSENT -> DOWNLOADING -> AVAILABLE
                                                                            (terminal: FAILED)
```

`AUTOMATIC_STATES = {WAITING_KEY, WAITING_PROVIDER, WAITING_NETWORK, DOWNLOADING}` - `WAITING_CONSENT` is deliberately excluded (a human decision, not something a tick should silently advance past). `handle_offer()` is the entry point for a real inbound `OFFER`; `AUTOMATIC_STATES` ordering mirrors WAITING_KEY's priority over the provider check - an OFFER from an unknown sender always lands in `WAITING_KEY` first, regardless of whether its `provider_id` is even resolvable.

**PR 1 (recoverable missing-key workflow):** `WAITING_KEY` is not a dead end. Two halves make it recoverable:

- **Trust gate (admission + resume)** (`receiver.handle_offer()` + `receiver._step_waiting_key`): an OFFER is authorized only when `get_binding_by_key_id()` resolves to an **`MCA_READY`** binding (`tofu_confirmed_at` set, no pending rotation). A `KEY_UNVERIFIED` binding (KEY_ANNOUNCE delivered, never confirmed) or a `KEY_CHANGED` one (a conflicting key is pending accept/reject) parks the transfer - an unverified key never authorizes a file, at either boundary.
- **Automatic key request** (`AttachmentsService._auto_request_missing_keys`, run once per tick): for every `WAITING_KEY` row whose signer's key is still unknown (`get_binding_by_key_id() is None`), send a `KEY_REQUEST` to its persisted reply route, under the layered safeguards described below. Idempotent (rate-limited to one request per window) and restart-safe (the row, its pending OFFER, and the throttle timestamp are all persisted).

**PR 1 correction pass (post-review):** seven refinements close gaps in the first PR 1 shape, each with dedicated regression tests:

1. **Trust gate at admission** (`receiver.handle_offer()`): the original gate only fired on *resume*; a `KEY_UNVERIFIED`/`KEY_CHANGED` binding that already existed when the OFFER arrived used to let it proceed straight past `WAITING_KEY`. Now `binding_ready = binding is not None and binding.status == AddressStatus.MCA_READY` is evaluated at admission: a non-ready binding parks the OFFER (storing `pending_offer_cbor`, leaving `sender_principal_id` `NULL`), never authorizes it.
2. **Per-canonical-address dedup within a tick** (`_auto_request_missing_keys`): an `attempted` set marks each address *before* decode/send, so two rows from the same address cannot both send in one tick - the dedup covers failed and rate-limited attempts too, not just successful sends.
3. **Canonical node-id validation at the common inbound boundary** (`_process_one_inbound_event`, immediately after `adapter.ingest()` and before any message-type dispatch): for the DIRECT-only MVP the transport event's `source_address`, the envelope's `source_address`, and the envelope's `route_id` must all be the same canonical `![0-9a-f]{8}` node id. A non-canonical or internally-mismatched source is dropped outright before a `KEY_REQUEST`/`KEY_ANNOUNCE`/`KEY_ACK`/`OFFER`/attachment ACK can be processed - so it can never create a key binding, trigger a key reply, create an attachment, or apply an ACK. This supersedes the earlier OFFER-only `_is_contact_id()` check, which guarded one message type and only the bare `source_address`, not the full route identity.
4. **Persisted workspace-wide hourly quota** (`KeyExchangeCoordinator`, migration 15, `mca_auto_key_request_quota`): automatic `KEY_REQUEST`s are bounded by `DEFAULT_MAX_AUTO_KEY_REQUESTS_PER_HOUR = 12` per workspace per hour, independent of the per-address rate limit and the per-tick cap (`MAX_AUTO_KEY_REQUESTS_PER_TICK = 8`, kept as an additional safeguard). `check_auto_key_request_quota()`/`record_auto_key_request_sent()` mirror the announce-quota pattern; the counter is persisted so a restart does not reset it, and mid-scan exhaustion stops the scan rather than overshooting the budget.
5. **Complete persisted reply-route validation** (`_auto_request_key_for_row`): before sending an automatic `KEY_REQUEST`, every persisted reply-route field is selected and verified - `reply_adapter_id` must equal the live `delivery_adapter.adapter_id`, `reply_connector_profile_id` must equal `delivery_adapter.connector_profile_id`, `reply_route_type` must be `DIRECT`, `reply_route_id` must be canonical `![0-9a-f]{8}`, and `reply_destination_address` must equal `reply_route_id`. A `NULL` or mismatched field fails closed (logged, row skipped) - the same validation shape the existing ACK-outbox path already applies. Regression tests cover `NULL` and per-field mismatch.
6. **No automatic key request for an expired `WAITING_KEY` row** (`_auto_request_key_for_row`): a row whose `hard_expires_at <= now` is skipped - no `KEY_REQUEST` is sent for a transfer that has already expired. The boundary (`hard_expires_at == now`) is tested explicitly. The actual `WAITING_KEY -> EXPIRED` state transition is owned by PR 2; this PR only suppresses the doomed key request.
7. **File-backed hourly-quota persistence proof** (test): the quota-survival regression test is strengthened to use a real file-backed `sqlite3` database - exhaust the quota, close and reopen the connection, construct a fresh `KeyExchangeCoordinator` and `AttachmentsService`, and prove the persisted quota still blocks automatic sends until the hour window advances (injected `now_fn`). This guards against a quota that only survives in a cached in-memory counter.

**Deferred (explicit handoff, PR 4) — safe public key-request state projection.** The correction pass asked for a "safe public key-request state projection" so the UI can show whether a `KEY_REQUEST` may currently be sent to a contact, without exposing raw key material or the throttle's internals. This is **documented as owned by PR 4 (the Files-workspace / MCA Contacts UI work) rather than implemented here**, because it is a user-facing UX surface layered on top of the backend reliability fixes this PR corrects. The contract is fixed here so PR 4 implements it against a stable, race-safe shape. The public response exposes, per contact:

- a derived boolean **`can_request_key`** and a **`key_request_state`** enum of **`idle` / `queued` / `waiting_response` / `retry_available`**: `idle` = no request in flight and none needed; `queued` = a request is enqueued but not yet on the wire; `waiting_response` = a request has been sent and the reply is pending; `retry_available` = a prior request's cooldown has elapsed and another may be sent. These are UI affordance states, derived on read - never persisted, never a raw storage field.
- **no exact throttle timestamp and no raw key material**: the projection is computed from `mca_key_exchange_contact_state.last_request_sent_at` against `MIN_SECONDS_BETWEEN_KEY_REQUESTS_TO_SAME_ADDRESS`, but `last_request_sent_at` itself and the raw `public_identity` bytes are never returned - the client must not learn the exact throttle timestamp or the raw public identity. (The key-material projection already shipped - `recipient_snapshot.py`'s `RecipientBindingSnapshot` and `api_attachments.py`'s `_serialize_contact` - already exposes only non-secret fields and never `public_identity` or `last_request_sent_at`; the manual `contact_request_key` command already surfaces a throttled request as `error_code="rate_limited"` with no timestamp leaked. The new pre-emptive projection extends that discipline.)
- a **worker-published, race-safe projection**: read-only, computed on the worker thread's connection (or from an atomically-published snapshot like `RecipientSnapshot`), never by a REST thread reading `conn` directly, per the single-owner SQLite model (§4).

Acceptance criteria for PR 4:

- `can_request_key` must be authoritative only for the *request-key* affordance: it must not be treated as a general "contact healthy" signal, and a `KEY_UNVERIFIED`/`KEY_CHANGED` contact must still show as *requestable* where that is the correct next action (distinct from `MCA_READY`, which should not).
- Add a test proving the serialized contact payload never contains `last_request_sent_at` or `public_identity` (the existing `recipient_snapshot`/`_serialize_contact` tests already assert this for the key material; extend the same discipline to the new projection).

## 4. Single-owner SQLite model (PR #231 review, section 2)

Every MCA-related table lives in one `sqlite3.Connection` per workspace (ADR-0003's documented exception to "no database, only JSON files"). Before the PR #231 hardening pass, both the radio listener thread and `AttachmentsService`'s worker thread could reach this connection directly, serialized only by a shared `threading.Lock` - a real hazard, since any new call site that forgot to acquire that lock would silently race. The shipped fix makes `AttachmentsService`'s own worker thread the **sole** owner of the connection at runtime:

- `mca_runtime.handle_incoming_meshtastic_text()` (called from the radio listener thread) does exactly one thing: build an immutable `service.InboundEvent` (raw text, source address, packet id, timestamp) and hand it to `AttachmentsService.enqueue_inbound()` - a bounded (`INBOUND_QUEUE_MAXSIZE=256`), non-blocking `queue.Queue`. `put_nowait()` either succeeds immediately or raises `queue.Full`, caught and logged as a dropped event (source address only, never message contents) - the radio listener thread never blocks on this call.
- `AttachmentsService._drain_inbound_events()` runs at the start of every `tick()`, draining up to `MAX_INBOUND_EVENTS_PER_TICK=16` queued events and dispatching each via `_process_one_inbound_event()` - the CBOR decode (`delivery_adapter.ingest()`), message-type classification, `KeyExchangeCoordinator.handle_incoming()` or `receiver.handle_offer()` call, and any resulting reply-send all happen here, on the worker thread, holding the one connection.
- `AttachmentsService.tick()` is guarded by its own **dedicated** `threading.Lock` (`_MCARuntimeState.tick_lock`, constructed fresh - never `mca_runtime`'s own module-level `_lock`) so repeated/concurrent calls to `tick()` itself are safely serialized; this is no longer about arbitrating two different threads' *direct* database access, since only the worker thread does that any more.
- The worker's first `tick()` runs immediately on `start()`, rather than waiting out the full `tick_seconds` interval - a freshly-started service (or one recovering from a restart) resumes pending work without an up-to-5-second idle gap.
- `AttachmentsService.stop(timeout=5.0)` now returns whether the worker thread actually stopped within the timeout; a caller that then closes the connection (`mca_runtime.reset_state_for_tests()`, the only real caller) checks this before doing so, rather than unconditionally closing out from under a still-running tick.

`AttachmentsService` is started unconditionally in `start_runtime()`, independent of whether the connected radio's identity matches the configured profile (PR #231 review, section 3) - a mismatched/unconfirmed identity blocks the *radio listener* (so no inbound message can arrive), but must never freeze previously-drafted/in-flight attachment work, which is unrelated to that question. `start_attachments_service()` also runs **before** the radio listener thread is started at all (`server.py`'s `start_runtime()`), not after - see the next paragraph for why order matters here, not just presence.

**2nd-pass correction:** the first version of this redesign still had an indirect blocking path. `handle_incoming_meshtastic_text()` used to call `ensure_service()`/`_get_state()` on *every* invocation, and both acquired `mca_runtime._lock` - which, at the time, was the *same* lock object `AttachmentsService` was constructed with for `tick()`'s own re-entrancy guard. Since `tick()` holds that lock for its entire duration - including `ConnectivityMonitor.refresh()`'s real Relay HTTP calls - a slow/unreachable Relay meant the radio listener thread could block for the same duration, exactly the hazard the redesign above was supposed to eliminate. Fixed with the dedicated `tick_lock` mentioned above, plus removing `ensure_service()`/`_get_state()` calls from `handle_incoming_meshtastic_text()` entirely: after startup, it only ever reads the already-built module-level runtime state directly and calls straight through to `enqueue_inbound()` - no lock, no database, no filesystem, no network. If the runtime is somehow not ready yet (should never happen given the startup ordering above), the event is logged and dropped - the listener thread never falls back to initializing the database or worker itself. See `tests/test_mca_runtime.py`'s `test_handle_incoming_meshtastic_text_does_not_block_on_a_slow_tick` (a fake Relay session that blocks until released, proving the fix directly) and `tests/test_server_mca_startup_wiring.py`'s `test_start_attachments_service_completes_before_listen_meshtastic_starts` (an AST-level ordering check).

## 5. TOFU and encryption

`KeyExchangeCoordinator`/`mca_recipient_bindings` (`meshsrv/attachments/key_exchange.py`) track, per `(workspace, adapter, transport_address)`, a recipient's currently-trusted public identity and status: `KEY_UNKNOWN` (no binding at all) / `KEY_UNVERIFIED` (seen, not yet confirmed by a human) / `MCA_READY` (confirmed, trusted) / a pending `KEY_CHANGED` state when a conflicting `KEY_ANNOUNCE` arrives for an address whose key is already trusted (parked in `pending_public_identity` until explicitly accepted or rejected).

`get_binding_by_key_id()` is a second, address-agnostic index into the same table, used for `OFFER` signature verification - correct there, since a signature verifies the *signer's* identity regardless of which physical address relayed the message.

**TOFU-to-transport-address binding before encrypting (PR #231 review, section 8; tightened again in the 3rd pass):** `AttachmentsService._resolve_recipient_identities()` resolves a draft's recipient key_id(s) to public identities for the `ENCRYPTING` step. An earlier fix (PR #227 defect #6) excluded any binding that was not `MCA_READY` - correct, but incomplete: it never checked that the binding's own `transport_address` matched the attachment's actual delivery destination (`attachment_deliveries.route_id`). A later fix (2nd pass) added that address check, but only when a delivery record happened to already exist and be `DIRECT` - a *missing* delivery record or a non-`DIRECT` one silently skipped the check entirely (fail open), letting an otherwise-trusted recipient through with nothing verified about the destination at all.

The 3rd-pass fix requires, in this fixed order, before resolving any individual recipient - any failure excludes every recipient (an empty mapping, which `_step_sent()` already turns into `fail_recipients_not_trusted()` for the whole attachment):

1. an `attachment_deliveries` record exists at all (`create_draft()`'s own required `adapter_id`/`connector_profile_id`/`route_type`/`route_id` parameters mean a normal attachment always has exactly one - a missing row is a data-integrity problem, not a shape the API can produce);
2. that delivery's `route_type` is `DIRECT` (the only route shape this MVP creates or knows how to verify an address against - a channel broadcast's `route_id` names the channel, not any one recipient's address, and channel delivery is out of scope for this review);
3. that delivery's own `adapter_id` matches this service's actually-configured `delivery_adapter.adapter_id` (encrypting for a delivery record naming a different adapter than the one about to send is the same "trust the key, not the destination" gap, one field over);
4. only then, each individual recipient's binding: `binding.transport_address` must equal the delivery's `route_id`.

Rejection log lines name only *which* check failed, never a raw transport address, key_id, or attachment_id - a dedicated test asserts this across all four rejection paths in one pass, so the rejection mechanism itself cannot become a secondary channel for exactly the identifying data TOFU exists to protect.

## 6. Connectivity (`meshsrv/connectivity_monitor.py`, ADR-0008 §2 + PR #231 amendment)

`ConnectivityMonitor.refresh()` (called once per `AttachmentsService.tick()`, never from a request handler) probes every registered Relay profile's `/health` (frequent, backing off exponentially on consecutive failure, capped at `RELAY_HEALTH_BACKOFF_CEILING_SECONDS`) and, rarely, `/v1/info` (identity + protocol-version confirmation). See `MCAttach_Multi_Relay_Requirements.md` for the full multi-Relay behavior and `ADR-0008`'s amendment for the specific bugs this hardening pass fixed (fallback-check trigger, disabled-profile staleness, transient `/v1/info` failures, stale-provider pruning).

`can_attempt_relay(provider_id)` is advisory only - `AttachmentsService` uses it to decide whether a tick is worth attempting a real network call for a given attachment, but the real HTTPS attempt inside `sender.run_step()`/`receiver.run_step()` remains the final authority regardless of what the monitor last reported.

**Independent internet status even when every Relay is disabled (2nd-pass correction).** `refresh()`'s fallback-internet-probe trigger used to also require `(not profiles or any_failing)` before running - since a *disabled* Relay was deliberately excluded from `any_failing` (a disabled profile is a user choice, not a failure), a workspace whose only registered Relay(s) were all disabled never reached the fallback probe at all, leaving `internet` status frozen (typically `UNKNOWN` forever) instead of independently reflecting general reachability. Fixed: the fallback probe now runs whenever there is no confirmed `ONLINE` evidence from any Relay (`any_online is False`), regardless of *why* - no profiles, all disabled, all failing, or a mix - subject to the same due-timing as before.

**Bounded concurrent Relay probing (3rd-pass addition).** `refresh()` used to probe due Relays strictly one at a time - a single slow/unreachable Relay could delay probing another, already-due Relay behind it in the same pass by up to the full request timeout. `_probe_relay()` is now a pure function with respect to `self` state (it reads only `self._timeout`, plus caller-supplied `current_failures`/`last_info_check_at` values and its own freshly-acquired session - see below - and returns a `_RelayProbeResult` bundle - it never writes any of the monitor's own dicts and never calls `ProviderRegistry.record_check_result()`, the SQLite write). `_probe_due_relays_concurrently()` dispatches up to `MAX_CONCURRENT_RELAY_PROBES` (2) of these via a bounded `ThreadPoolExecutor`; `refresh()` itself still applies every result - the actual state mutation and the SQLite write - sequentially, back on the calling thread (`AttachmentsService`'s own worker thread, inside its `tick_lock`), after the pool returns. Per-profile cadence, backoff, and identity/protocol checks are unchanged.

**Per-probe HTTP sessions, never shared across concurrent workers (4th-pass correction).** The 3rd-pass addition above shipped with every concurrent probe worker sharing one `self._session` instance, and a docstring incorrectly describing `requests.Session` as documented thread-safe for concurrent requests - it is not: `requests`' own docs only claim the underlying `urllib3` connection pool is safe to share across threads, not the `Session` object itself, which carries mutable per-instance state (cookies, hooks, adapters) a concurrent caller can race on. `ConnectivityMonitor.__init__` now accepts an optional `session_factory: Callable[[], Any]` (defaulting to `requests.Session` itself - a brand-new instance every call); `_probe_relay()` calls it fresh for every probe and closes that session deterministically (`_close_session()`, `finally`-guarded) once the probe returns, success or failure. `_check_fallback_internet()` was fixed the same way - it previously read `self._session` directly. The pre-existing `session=` constructor parameter is kept for backward compatibility: it is wrapped internally into a factory that always returns that one given object - explicit, single-shared-session semantics a caller opts into knowingly (safe for a stateless test double; not a substitute for `session_factory` against a real `Session` under real concurrent I/O). The `MAX_CONCURRENT_RELAY_PROBES` (2) ceiling is unchanged. A regression test using production-shaped session objects tracked by instance id proves two concurrently in-flight probes use genuinely different instances *while one is still blocked* (not merely "they differed after the fact"), and that every session the factory ever created is closed by the time `refresh()` returns.

**Structured contextual upload readiness (`evaluate_upload_decision()`, 3rd-pass - supersedes the 2nd pass's `can_upload_to()` boolean).** `RelayStatus.state` and `.upload_readiness` are reported side by side, deliberately independent (§10 below) - but neither alone answers "is it actually sensible to start an upload to this Relay right now, with this ciphertext, for this TTL", and `ProviderRegistry.get_upload_candidates()` filters purely on local config with no live-state awareness. `evaluate_upload_decision(provider_id, *, ciphertext_bytes=None, requested_ttl_seconds=None) -> UploadDecision` checks, in order, returning on the first failure: the profile exists; it is `enabled`; `upload_allowed`; a credential is configured; the Relay's live `RelayState` (`UNKNOWN` maps to its own `RELAY_NOT_YET_CHECKED` reason - deliberately *not* fail-open here, unlike `can_attempt_relay()`, since a human-facing "can I upload" answer should not claim readiness this module has not actually confirmed; `UNREACHABLE`/`IDENTITY_MISMATCH`/`INCOMPATIBLE` each get their own reason; `DEGRADED` counts as ready, matching the existing `_ATTEMPTABLE_RELAY_STATES` meaning elsewhere); and, when the caller supplies them, the actual ciphertext size against `max_ciphertext_bytes` and a requested TTL against `min_ttl_seconds`/`max_ttl_seconds`. `UploadDecision(ready, reason, detail)` is a structured result, not a bare boolean - every rejection is a named `UploadRejectionReason`. The old `can_upload_to()` is kept as a thin `bool` wrapper for callers that only need yes/no. `AttachmentsService.evaluate_upload_readiness()` is the service-layer surface Step 1.6A's future REST endpoints should call (thin delegation, matching this module's own "API handlers never touch the Relay/radio themselves" rule) - `sender.py`'s actual encrypt/upload pipeline is left unchanged, since its ciphertext size is only known mid-`ENCRYPTING`, and gating it there is left as its own reviewed step rather than folded into this connectivity-layer fix.

**All profile reads inside `evaluate_upload_decision()` come from an in-memory snapshot, never SQLite directly (4th-pass correction).** The function above originally read `self._provider_registry.resolve(provider_id)` on whatever thread called it - a live SQLite read from outside the single owning worker thread, the exact hazard the 2nd-pass amendment's single-owner-SQLite redesign (§1) was meant to close everywhere, missed here because this function predates that redesign's own audit. `ConnectivityMonitor` now maintains `self._profile_snapshot: Dict[str, ProviderProfile]`, published via a single whole-dict reference reassignment (`self._profile_snapshot = {...}`, never mutated in place - atomic under the GIL, so a concurrent reader sees either the old dict or the new one, never a partially-updated one). It is built once eagerly at the end of `__init__` (construction always happens on the startup thread, never a REST thread) and republished by `refresh()` (the `AttachmentsService` worker thread, inside its `tick_lock`) - the only two call sites of `_refresh_profile_snapshot()`. `evaluate_upload_decision()` reads only `self._profile_snapshot.get(provider_id)`, so it is both correct before the first `refresh()` (the constructor's eager build already covers it) and safe to call from any thread thereafter, including a future Step 1.6A REST handler. A deterministic thread-identity test wraps `ConnectivityMonitor`'s own `provider_registry` reference in a call-tracking proxy, invokes `evaluate_upload_decision()` from a separate simulated "REST" thread, and asserts zero registry calls were recorded from that thread; reverting the fix makes this same test reproduce a genuine `sqlite3.ProgrammingError` ("SQLite objects created in a thread can only be used in that same thread"), confirming this was a live, reachable bug and not a style preference.

## 7. Receiver-side ACK outbox (`meshsrv/attachments/receiver.py`, PR #231 review section 4)

A queued receiver-side reply (`mca_outgoing_replies`) is dispatched by `AttachmentsService._dispatch_outgoing_replies()`, once per tick, after the row-scan:

- **Real reply-route persistence.** An inbound `OFFER`'s reply route is now persisted with the actual adapter/connector that received it (`reply_adapter_id`, `reply_connector_profile_id`, `reply_route_type`, `reply_route_id`, `reply_destination_address` - migration 10, extended in this hardening pass), built from the `DeliveryEnvelope` the ingest step produced, not assumed to be "the one global Meshtastic adapter".
- **`DeliveryReceipt.sent` is actually checked.** `adapter.send()` returning without raising an exception does not by itself mean the message was sent - `receipt.sent is False` is now treated exactly like a raised exception (stays `PENDING`, attempt counted, backoff scheduled).
- **Real, persisted rate limiting.** `check_and_record_reply_quota()` (backed by the `mca_ack_quota` table) enforces both a per-source-address window (`ACK_PER_SOURCE_LIMIT=5` per `ACK_PER_SOURCE_WINDOW_SECONDS=600`) and a global window (`ACK_GLOBAL_LIMIT=30` per `ACK_GLOBAL_WINDOW_SECONDS=3600`), replacing the previous "N rows per dispatch call" limit, which only ever bounded one SQL query's row count, not the actual send rate. A reply that would exceed either quota is left `PENDING` and retried later - never marked sent, never dropped, and neither counter is incremented on a rejected attempt.
- **The persisted reply route is now fully consumed - both `adapter_id` and `connector_profile_id` (3rd-pass correction, superseding an incomplete 2nd-pass fix).** `reply_adapter_id`/`reply_connector_profile_id`/`reply_destination_address` were persisted from the very first hardening pass but not actually read by `_dispatch_outgoing_replies()` at all until the 2nd pass - and even that fix only validated `adapter_id`, silently ignoring `connector_profile_id` (`MeshtasticTextAdapter` gained a real `connector_profile_id = "meshtastic"` attribute, matching what `ingest()`'s own default already produced, specifically so there is something concrete to validate against). Both are now required and strictly validated - either missing or mismatched against the dispatching service's own `delivery_adapter` is `UNDELIVERABLE`. This is also a deliberate tightening from the 2nd pass's own behavior: that pass treated a *missing* `adapter_id` as "unknown, trust the currently-configured adapter" (permissive); the 3rd pass fails closed on a missing identity too, the same as a confirmed mismatch - consistent with the fail-closed posture applied everywhere else in this review (TOFU binding, inbound-OFFER admission, delivery-record requirements below). In production this never matters - `AttachmentsService._process_inbound_offer()` always builds a full `ReplyRoute` from the real `DeliveryEnvelope`; only this module's own non-integration tests ever used the simpler `source_address`-only shape, and those that specifically test real ACK dispatch now pass a full `ReplyRoute` too. The Route's own destination uses the persisted `destination_address`, not the bare `route_id` (a real regression test dispatches to a `destination_address` deliberately set apart from `route_id` and confirms delivery lands there, not at `route_id`).
- **Inbound OFFER admission limits (3rd-pass addition).** The transfer_id dedup in `handle_offer()` only protects against a *repeated* transfer_id - nothing previously bounded how many `attachments` rows a flood of OFFERs carrying distinct, attacker-chosen transfer_ids could create, each one a permanent row until it resolved or expired. `_would_exceed_inbound_admission_limit()` now rejects a new OFFER outright (before any row is created) once either a per-source ceiling (`MAX_PENDING_RECEIVED_PER_SOURCE=20`, counted against live non-terminal `received` rows sharing the same `reply_route_id`) or a workspace-global ceiling (`MAX_PENDING_RECEIVED_GLOBAL=200`) would be exceeded. The global ceiling is tested by actually spreading a flood across many distinct sources (each safely under its own per-source limit) to confirm the rejection is the global check firing, not a coincidental per-source one.

## 8. Migrations (`meshsrv/attachments/db/migrations.py`)

`migrate()` applies each pending migration inside an explicit `BEGIN`/individual-`conn.execute()`-per-statement/`COMMIT` sequence, with `PRAGMA user_version` updated as part of the same transaction. This was changed in the PR #231 hardening pass after empirically confirming (direct testing, not assumption) that Python's `sqlite3.Connection.executescript()` does **not** honor an explicit outer transaction on this project's build - statements that executed successfully before a later failure in the same script stayed committed even after an explicit `conn.rollback()`. The fix splits each migration's SQL into individual statements (`_split_sql_statements()`, comment-stripping regex + `;`-split) run one at a time via `conn.execute()`, which does roll back correctly on failure - verified directly, including for `PRAGMA user_version` itself. `tests/test_mca_db_migrations.py` covers upgrade/downgrade/re-upgrade round trips per version, an injected-failure-then-retry pair, and migration-9's data-fixup precision. `ALL_TABLE_NAMES` (the schema-completeness set every `issubset(...)` assertion in that file checks against) was missing `mca_ack_quota` (2nd-pass correction) - added by the same Migration 10 extension as `mca_outgoing_replies` but never registered here, so those tests silently never verified this table's presence. Migration 10's own dedicated test coverage (3rd-pass addition) now explicitly checks every reply-route column (`reply_adapter_id`/`reply_connector_profile_id`/`reply_destination_address`, not just `reply_route_type`/`reply_route_id`) and `mca_ack_quota`'s exact column shape, through upgrade, downgrade, and a full downgrade-then-re-upgrade round trip with a real row written before the downgrade - confirming the re-created table is genuinely functional, not just present by name.

## 9. Provider Registry v2 (`meshsrv/attachments/provider_registry.py`, ADR-0008 §3 + PR #231 hardening)

See `MCAttach_Multi_Relay_Requirements.md` for the full behavioral contract. Backend validation (`kind`, `display_name`, `max_ciphertext_bytes`, the TTL pair, `protocol_version`) and the `CLEAR` sentinel for explicitly nulling an optional field (distinct from "not mentioned", which the original `COALESCE`-based `update_profile()` could not express) were added in the PR #231 hardening pass. Step 1.6A.4 added `MAX_PROVIDER_PROFILES = 8` (enforced worker-side in the same transaction as the insert, so a rejected registration consumes no slot; re-registering the same derived `provider_id` is idempotent and consumes none either) plus `MAX_UPLOAD_TOKEN_BYTES = 4096` on `set_upload_token()` (`upload_token_too_long`). Two new companion modules back the two-phase onboarding and the hardened relay HTTP path: `probe_registry.py` (single-use, in-memory, TTL-bounded `ProbeRecord`s — probe then register with fingerprint confirmation) and `relay_http.py` (the shared §12 SSRF policy: `resolve_host_ips` / `is_globally_routable` / `validate_origin_routable` / `SecureSession` / `_PinnedHTTPSAdapter` / `build_secure_session`), with the eight provider command handlers wired in `meshsrv/attachments/service.py` and enqueued from `api/api_attachments.py`.

## 10. Upload readiness (`meshsrv/connectivity_monitor.py`)

`evaluate_upload_readiness(profile)` (a public function; previously a private `_upload_readiness_for()`) computes `ready | upload_token_missing | upload_disabled` from a profile's local configuration alone (`upload_allowed`, `upload_token_configured`) - **it does not read `profile.enabled` at all**, deliberately independent of live `RelayState`, since a Relay can be `upload_readiness=ready` while currently `UNREACHABLE`, or vice versa; the two are reported side by side, never merged. `LIMIT_EXCEEDED` was removed - nothing in this codebase computes a per-Relay upload quota. `RelayStatus.upload_readiness` shows `UPLOAD_DISABLED` for a disabled profile in `ConnectivityMonitor.refresh()`'s snapshot only because `refresh()`'s own disabled-profile branch constructs that value directly, bypassing this function entirely - calling `evaluate_upload_readiness()` itself against a disabled-but-otherwise-configured profile returns `READY` (see §6 above's `evaluate_upload_decision()`, the one function that actually checks `enabled`, precisely because this one and `refresh()`'s disabled-branch literal do not agree on that point and must not be conflated).

## 11. Install-time dependencies

`cbor2`, `PyNaCl` (`nacl`), and `requests` are Core (not adapter) dependencies - MCAttach code imports them directly, and none of the three carry a GPLv3 license concern the way `meshtastic` does, so they live in the repo root `requirements.txt`, not under `adapters/`. `scripts/verify-install.sh` includes an import check for all three so a broken/incomplete `pip install` on a fresh Pi surfaces immediately rather than as a runtime `ImportError` the first time an MCAttach code path actually executes.

`meshsrv/update_service.py`'s `apply_update()` detects (never installs - see its own comment on why running pip from inside the live Flask process would be its own hazard) whether `requirements.txt`/`adapters/meshtastic/requirements.txt` changed, using a plain `git diff --name-only HEAD <upstream>` **before** running `git merge --ff-only` at all (3rd-pass correction, superseding a 2nd-pass version that merged first and only detected the change afterward, leaving a merged-but-possibly-broken tree behind even though it correctly skipped the follow-on restart). If anything changed, `apply_update()` never calls `git merge`: `HEAD` and the working tree are left completely unchanged (confirmed directly by tests against real local git repositories, not just asserted), and the result carries the changed file list plus concrete manual install/restart instructions. `POST /api/updates/apply` returns `409` with `blocked=true` in that case - a distinct, non-error outcome, never `ok=True` - and never schedules a restart. `static/chat-updates-security.js` shows a persistent result panel with the manual instructions (not a transient toast) and re-enables the apply button; a dependency-free frontend test (Node's built-in `vm` module against the real script source - this project has no JS test framework, `node --check` is CI's only JS coverage) confirms `pollAfterUpdateRestart()`'s own polling target (`/api/system/info`) is never fetched on the blocked path.
