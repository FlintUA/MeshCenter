# MeshCenter v1.11.0

Range: `v1.10.0..main` (`5987d7d`), PRs #347, #350, #355.

**This release can be applied from the Updates card.** `requirements.txt`, `adapters/meshtastic/requirements.txt`, `install.sh`, the systemd unit, the sudoers files and the installer files are unchanged since v1.10.0 (the only startup file touched is `wsgi.py`, whose log format changes only when running in a container), so no package install or manual step is needed. Open **Workspace → System → Updates**, press **Check now**, then **Update** (it appears once v1.11.0 is published), or `git fetch --tags && git merge --ff-only origin/main` followed by `sudo systemctl restart meshcenter.service`. As with any update, keep a copy of `data/` and `config.py`.

## Docker (new)

- MeshCenter now runs in a **single container** on Linux amd64 - built and tested on a Synology DS920+ - with the radio connected **over TCP only** (no USB serial, Bluetooth, camera, I2C or e-Paper inside the container). One container, two processes, two Python environments: the GPLv3 `meshtastic` package stays in the adapter's own environment, exactly as on a Raspberry Pi install. Data and configuration live on two volumes (`/data`, `/config`); `config.py` is created once from a template and never overwritten. Step-by-step Synology/DSM instructions, the `docker save` / `docker load` transfer, and troubleshooting are in `docs/Docker_Installation.md` (#355)
- **The image is not published.** It contains the GPLv3 `meshtastic` package, and redistributing a prebuilt image waits on the open licensing documentation item (D0 §5, see `THIRD_PARTY_NOTICES.md`). Build it locally with `deploy/docker/build.sh`, which labels the image with `git describe` (for example `meshcenter:1.11.0`) (#355)
- In container mode, controls that only make sense on a host - reboot/shutdown, Wi-Fi/network, self-update, hardware configuration, host identity/temperature - are disabled with a notice instead of failing. A native install is unaffected: the switch is the single variable `MESHCENTER_RUNTIME=container`, which nothing outside the image sets (#355)
- `GET /healthz` (no login, GET only, returns just `{"status":"ok"}`) for container health checks. When there is no `.git` directory, the version comes from `MESHCENTER_VERSION` baked in at build time; a label that is not a version number (`dev`, `dk3`) never produces an "update available" message (#355)
- Container details worth knowing: the first visit goes to `/setup` to choose the password - do that straight away; the Synology host port 5000 is taken by DSM, so publish MeshCenter on another port (the docs use `5080:5000`); the untouched placeholder radio profile `!00000000` is hidden once a real radio is accepted (#355)

## TCP radio reliability (native and Docker)

- A new **TCP link supervisor** keeps a TCP radio connected on its own and never gives up. After a lost session it waits about 25 seconds (the radio needs that long to release its connection), then retries after 30, 60 and 90 seconds and then every two minutes; each attempt closes the old session, re-verifies the radio's identity and reconnects. A session counts as recovered only after it has stayed up for 20 seconds. A different radio answering at the same address is still refused, as before (#355)
- The header status and Node Manager show **"Reconnecting… (attempt N, next in X s)"** instead of a stale "Connected"; a connection that does not exist is never shown as connected. **Reconnect** for a TCP radio now makes an immediate attempt (`POST /api/meshtastic/reconnect_now`) and restarts the schedule; it no longer needs a saved Settings endpoint. Node Manager also shows **Link resets (last hour)** (#355)
- **One TCP client per radio.** A Meshtastic node serves a single TCP client and drops the old one when a new one connects, so two MeshCenter instances (or MeshCenter plus the phone app or a script) on the same radio evict each other and neither stays connected. If a radio keeps closing new sessions within seconds, Node Manager now says "the radio may be in use by another client" and retries more slowly. (#355)
- Teardown was made slot-safe: every closed connection is shut down first (a plain close did not release the radio's connection on Linux, so an abandoned handshake blocked the radio for about two minutes), our close answers the radio's within milliseconds, and a closed connection never sends the library's 5-minute heartbeat again. The Meshtastic library's own silent re-dial, which could leave a link showing "Connected" for hours while the radio was away, is disabled in favour of the supervisor (#355)
- Reconnects ask the radio for its configuration only, without its node database: measured on a T-Beam with 100 nodes, 14 kB became 1.2 kB and the connect took 0.8 s instead of 1.4 s; identity, name, hardware and firmware come through identically. The first connection after a start still loads the full node list (#355)
- Each lost session is logged with its age, bytes and the radio's uptime, and a radio reboot (uptime going backwards) is recorded as one (#355)
- Listener auto-recovery no longer runs for TCP or Bluetooth radios (there is no serial listener to restart), and a TCP connect no longer triggers the serial-port release path (#355)
- A direct message encrypted with the recipient's key (PKI) now reports its channel as unknown instead of channel 0, which removes a warning about a channel mismatch on every incoming MCAttach message over TCP (#355)

## MCAttach

- **`MCA_CONTROL_CHANNEL_INDEX` must be set** in `config.py` (the index, 0-7, of your private channel) for MCAttach to work; there is no default, so that control traffic can never go out on the public channel by accident. If it is unset, MCAttach transfers are refused and a **warning is logged at every start** (System Log and console). The Docker template documents the setting (#355)

## Security and robustness

- Unexpected server errors answer with a generic message and an `error_id`; the cause is written to the log under that id instead of being returned to the browser. "Profile not found" no longer returns a server path (#347)
- Marking a chat as read is an explicit, CSRF-protected request that is confirmed only after it has been saved; `GET /api/messages` no longer changes anything (#350)
- Node Manager errors (radio discovery, accepting or switching a radio) appear as an in-page notice instead of a browser `alert()` box (#355)

## Docs

- `docs/Docker_Installation.md` (new) and `docs/architecture/docker-blockers.md`; the TCP section documents the radio's single-client behaviour and what "Link resets" means (#355)
- `deploy/docker/build.sh` and the compose template; `CLAUDE.md` describes the supervisor and the container switch (#355)

## Upgrade notes

- **The Updates card works for this release** - no dependency or installer changes.
- **TCP radios: make sure nothing else is connected to the same radio** (a second MeshCenter, the phone app, a script). The new supervisor reconnects automatically, but a competing client will keep taking the connection away.
- **If you use MCAttach, set `MCA_CONTROL_CHANNEL_INDEX`** (see above); without it MCAttach is refused and a warning is logged at startup.
- The "TCP/Bluetooth Auto-Reconnect" setting is still honoured for TCP: with it switched off, only the **Reconnect** button reconnects.
- Serial and Bluetooth radios are not affected by the TCP changes.

## Known issues

- **Intermittent CI hang:** one CI run stalled for about eight minutes in `tests/test_server_startup_tcp_transport.py` and was cancelled; the same commit passed on rerun and the test file passes on its own. The cause is not found. It does not affect a running installation.
- **A misleading "Radio profile restart failed … died with SIGTERM" entry** is written to the System Log at every profile switch even though the restart works (the restarting service kills the process that issues the command). Harmless; to be silenced in a later release.
- When two clients contend for one radio, the sessions alternate (about 30 seconds each) rather than one winning; the contention notice only appears when sessions end within 20 seconds.

## Known limitations

- The Docker image is Linux amd64 only and TCP only. It is not published; build it yourself.
- TCP has a narrower receive scope than serial: no routing acknowledgements (so no delivery ticks for direct messages over TCP), no remote waypoint deletion, and an event that arrives while there is no session can be lost.
- Bluetooth (BLE) is send-only - nothing is received while it is the active transport.
- If a *different* radio is plugged into the serial port after an unplug, MeshCenter halts and asks you to confirm; covered by automated tests, not verified live with a second physical radio.
- Message and chat-list times use a fixed 24-hour format and do not follow the 12h/24h toggle (KI-007).
- During quiet operation the serial listener can occasionally restart on its own, with a brief "listener down" blip in the health display (KI-009: pre-existing and cosmetic).
- USB MJPEG passthrough has not been live-verified against a real MJPEG-capable camera.
