# MeshCenter v1.12.0

Range: `v1.11.0..main` (`751c8ce`), PRs #357 (ST1) and #360 (RR1).

**This release can be applied from the Updates card.** `requirements.txt`, `adapters/meshtastic/requirements.txt`, `install.sh`, `meshcenter-firstboot.sh`, the systemd unit, the sudoers files, `gunicorn.conf.py` and the Dockerfile are unchanged since v1.11.0, so no package install or manual step is needed. Open **Workspace → System → Updates**, press **Check now**, then **Update** (it appears once v1.12.0 is published), or `git fetch --tags && git merge --ff-only origin/main` followed by `sudo systemctl restart meshcenter.service`. As with any update, keep a copy of `data/` and `config.py`. Docker users rebuild the image (see below).

## Stability and delivery ACKs (ST1, #357)

- **Direct messages now show real delivery.** A DM is "delivered" only when the destination node itself acknowledged it; a relay's implicit ack stays "sent", and any routing error is shown as "unconfirmed". Works on **serial** (the ACK is captured inside the send's own port claim, up to 12 s) and on **TCP** (routing ACK events from the radio, which were not received at all before). Bluetooth does not show delivery ticks.
- **Sends have priority over background work.** Channel reads, time sync and node refresh now wait while a send is queued or its ACK is outstanding, instead of racing it for the radio. A call that would have less than 5 s left after waiting for the lock is answered "busy" instead of being started and killed.
- **No more adapter kills from routine background work.** Channel discovery is single-flight with a 30-minute cache and a 60-second failure backoff; the radio clock is synced once per connection and then every 6 hours, and no longer after every listener restart.
- **Listener restarts are classified correctly.** A listener exit within 30 s of MeshCenter's own stop request is intentional (no error), health reports "paused" rather than "listener down" during it, and `[LISTENER EXITS]` counters in the log/health separate intentional from unexpected exits.

## Release radio (RR1, #360)

- **Release radio** (Node Manager and Settings) now works for **TCP as well as serial**, with a duration: **15 minutes, 1 hour, or until you press Reconnect**. While released, MeshCenter holds no connection to the radio, so the phone app or another tool can use it; a timed release ends by itself and the link reconnects. The header shows "Radio released" (informational, not an error) with a countdown, and the message composer is disabled with a hint instead of letting you send into a link that does not exist.
- **A TCP release survives a restart** (`data/profiles/<id>/radio_release.json`) — restarting the service or the container does not silently reclaim a radio you handed to another client. A serial release stays in memory only. Reconnect, an explicit connect, or activating the profile ends a release; boot and the link supervisor never do.
- **Contention detection for alternating clients.** If the radio keeps dropping MeshCenter's sessions because another client keeps taking it, Node Manager now says so and backs off (the notice clears after 15 minutes of a stable link). It never releases the radio by itself.
- Detecting or accepting a radio at an endpoint that is currently released is refused with "Radio released – press Reconnect" rather than competing with the client you released it for.
- **Node Manager auto-refreshes** (3 s while something is changing, 30 s otherwise) and never re-renders under you while the Discover form is open or you are typing in a field.
- Discover radio form polish: labels above inputs, Host and Port on one row, spacing fixes (also at phone width).
- Fixed: System Log entries written by the release/reconnect manager had shifted fields (the event column showed "ACTION"); the dashboard showed a wrong Host:Port after a restart while released.
- The old API-only setting `tcp_ble_autorecovery.enabled` is no longer consulted for TCP (it had no UI and did not stop boot or explicit connects); it still governs Bluetooth auto-reconnect.

## Upgrade notes

- **Updates card works** — no dependency or installer changes.
- **Docker users:** rebuild with `deploy/docker/build.sh` (image `meshcenter:1.12.0`, still not published) and point the compose file's `image:` at it. To let the phone app use the radio, press **Release radio** instead of stopping the container — the release survives a container restart, and **Reconnect** takes the radio back.
- **One TCP client per radio, still.** A Meshtastic node serves a single TCP client and drops the old one when a new one connects. Release the radio in MeshCenter before connecting the phone app (or any other tool) to the same node; otherwise the two evict each other. Release is the supported way to hand the radio over.
- Serial and Bluetooth users: delivery ticks and sends priority apply to serial; Bluetooth is unchanged.

## Known issues

- Base↔Echo-type DMs can return `NO_CHANNEL` NAKs when a radio pair lacks the other's public key; this is a key-exchange state of the radios, not MeshCenter, and shows as "unconfirmed".
- A release cannot be applied to Bluetooth (out of scope), and a serial release is lost on restart (KI-010).
- The misleading "Radio profile restart failed … died with SIGTERM" System Log entry at profile switch remains; harmless.
- The intermittent CI hang in `tests/test_server_startup_tcp_transport.py` (v1.11.0) has not recurred but its cause is unknown.

## Known limitations

- The Docker image is Linux amd64 only, TCP only and not published; build it yourself.
- TCP still does not receive remote waypoint deletion, and an event arriving while there is no session can be lost.
- Bluetooth (BLE) is send-only.
- Different-radio-on-replug (serial identity MISMATCH) is covered by tests, not verified live.
- Message times use a fixed 24-hour format (KI-007); the serial listener can occasionally restart on its own during quiet operation (KI-009).
