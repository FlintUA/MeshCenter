# PR 6 prerequisite — legacy `--mc-legacy-*` → canonical semantic token mapping table

Confirms/corrects the proposed mapping table for migrating `static/style-part4.css`'s `--theme-*`/`--mc-legacy-*` layer onto the canonical, family-aware `--mc-*` tokens (PR 6). **No code changes in this deliverable** — this is the research/planning artifact the 2026-09-05 scope decision asked for before PR 6 is briefed, per the same "recompute independently, don't trust the proposal blindly" discipline as every implementation PR in this project.

## Method

Read the current values directly off `main` (post-PR-5/-7, `static/ui-kit.css`'s canonical `:root`/`html[data-theme="dark"]` blocks and the `--mc-legacy-*` declarations inside them) — not copied from the proposal. Computed RGB Euclidean distance from every legacy token to **every** plausible canonical base candidate (surface/text/border/accent/control tokens, ~20-27 per mode, not just the name-matched one), light and dark, with a standalone script (not committed — throwaway, same convention as prior stages' `.theme_stage0_scratch/` verification scripts). Cross-checked every number the proposal cited; all matched to within 0.1 of my own recompute, which is worth stating plainly: the proposal's arithmetic is solid throughout. My corrections below are about **candidate selection and semantic judgment**, not arithmetic errors.

Live-verified the two components' *actual rendered* colors on `mc-dev` (dark mode) directly via `getComputedStyle()` against `.node-manager-panel`, `.device-hero-card`, `.node-profile-card` — real DOM elements, not just cross-referencing the CSS source — to confirm the panel/card swap finding has a real, visible consequence, not just a numeric one.

Also pulled the full `--theme-*`/compatibility-layer consumer counts directly from `static/style-part4.css` (not estimated) - see "Consumer counts" below - since knowing how much surface each token affects matters for how carefully PR 6 should treat each mapping decision.

## Notes

**1. `--mc-legacy-workspace-bg`/`--mc-legacy-app-bg` — light-mode exactness is a coincidence, not a signal.** Light `workspace-bg` (`#f7f9fc`) is bit-identical to `--mc-bg-subtle` (and, by extension, `--mc-surface-sunken`/`--mc-surface-control`, which PR 5 made identical to it) — but that's because canonical light's `--mc-bg-workspace` (`#f5f7fa`) and `--mc-bg-subtle` (`#f7f9fc`) already sit only 3.5 apart from each other; the legacy value happening to land exactly on one of two near-identical neighbors isn't meaningful. Same story for `app-bg` landing exactly on `--mc-bg-muted` instead of `--mc-bg-app` (d=1.4). Recommend keeping both **name-matched** (`workspace-bg`→`--mc-bg-workspace`, `app-bg`→`--mc-bg-app`): dark mode has no ambiguity (bg-workspace/bg-app are clearly the best semantic fit, 4.1 and 11.5 - both within this project's established "safe to alias" range), and picking a different target per mode for the same token would be a worse, mode-inconsistent pattern than accepting light's small, already-negligible non-zero distance. Flagging only so a future reader isn't confused finding a "closer" candidate in light and wondering why it wasn't used.

**2. `--mc-legacy-border`/`--mc-legacy-border-soft` — confirmed the proposal's read, including the recommendation to *not* chase the numerically-closer dark target.** My own recompute matches the proposal's dark numbers exactly (`--mc-legacy-border` → `--mc-button-secondary-border` at 15.6, vs `--mc-border` at 21.4; `--mc-legacy-border-soft` → `--mc-border` at 5.8, vs `--mc-border-soft` at 20.9). Agree with the proposal's judgment call: `--mc-button-secondary-border` is a control-specific role (already established as such by the family-block "border-control" convention this project uses elsewhere), and borrowing it for a *generic* body/card border would be a worse semantic fit than a d≈21 dark-mode nudge that's still well short of "genuinely distinct" by this project's own precedent (the smallest confirmed-distinct example elsewhere in this codebase is ~30+; d=21 sits in the ambiguous middle this project has previously resolved case-by-case, not automatically). Recommend **name-matched targets for both**, live-verified as the right call in "note 3" below (the border tokens sit *inside* the panel/card surfaces this note's swap already affects, so keeping border semantics simple matters for readability there).

**3. `--mc-legacy-panel-bg`/`--mc-legacy-card-bg` — the swap is real, confirmed live, and its consequence is worse than a color nudge: it inverts elevation hierarchy if implemented by name.** Live-checked on `mc-dev` (dark mode, current `main`): `.node-manager-panel` (the outer container, semantically "the panel") computes to `rgb(22, 36, 51)` = `#162433` - the *exact* value of canonical `--mc-card-bg`, not `--mc-bg-panel`. `.device-hero-card`/`.node-profile-card` (the inner cards, semantically "cards raised above the panel") compute to `rgb(28, 44, 61)` = `#1c2c3d` - closer to canonical `--mc-bg-panel`/`--mc-bg-muted` than to `--mc-card-bg`. Mapping by name would make the *panel* (currently darker, `#162433`) suddenly render as the *lighter* `--mc-bg-panel` (`#1b2837`), while the *cards* inside it (currently lighter, `#1c2c3d`) would suddenly render as the *darker* `--mc-card-bg` (`#162433`, canonical dark's `--mc-card-bg` is its own literal, not aliased to `--mc-bg-panel`) - cards would end up **darker than their own container**, inverting the raised-surface visual language this whole token system is built around. This is not a subtle color drift; it's a legibility/hierarchy regression. Confirms the proposal's swap direction. One refinement: my recompute finds `--mc-legacy-card-bg`'s dark value is numerically *slightly* closer to `--mc-bg-muted` (5.8) than to `--mc-bg-panel` (7.3, the proposal's pick) - both are comfortably in "safe to alias" range and the 1.5-unit gap is not meaningful, so I'd still recommend `--mc-bg-panel` for the clearer semantic fit ("a card reads as *the* raised-panel surface," matching how `.node-card`/`.settings-card`/etc. already use it elsewhere) - noting the near-tie so nobody is surprised finding `--mc-bg-muted` numerically ahead.

**4. `--mc-legacy-card-hover`/`--mc-legacy-elevated-bg` — confirmed, same category-mismatch tension as note 2, resolved the other way.** Both land closest to `--mc-button-secondary-bg` in dark (4.9, 7.8) with a comfortable margin over any generic surface token (next-closest is `--mc-border-soft`/`--mc-border` in the 9-12 range - not close). Unlike note 2's borders, there's no equally-clean name-matched alternative here (light's own best fits - `--mc-bg-workspace`/`--mc-bg-subtle` for card-hover, `--mc-bg-muted` for elevated-bg - don't carry over to a comparably strong dark candidate; the button-secondary family is the only tight match in dark for either). Given both these roles genuinely *are* hover/elevated-*control-adjacent* surfaces (not plain static content backgrounds), and this project's family-block docs already treat `--mc-button-secondary-bg` as the "surface-control" role, aliasing here is a legitimate reuse of an established convention (same reasoning PR 5 used to name its own `--surface-control` split), not a category-mismatch forced fit like note 2's borders would have been. Recommend live-verifying the actual hover interaction once implemented (a hover state briefly shown, harder to eyeball than a static panel) but the numeric case is solid.

**5. `--mc-legacy-focus`, light mode — confirmed real, and higher-priority than the proposal's framing suggested.** Dark aliases cleanly to `--mc-border-focus` (d=5.0). Light has no clean match at all (nearest is `--mc-border-active` at 55.6, `--mc-border-focus` itself at 59.5) - confirmed, matches the proposal's numbers exactly. Pulled the actual consumer count directly from `style-part4.css` (not estimated): **`var(--theme-focus)` appears 14 times** - a real, non-trivial surface, higher than several of the "clean" mappings above (`--mc-legacy-workspace-bg` has only 2 consumers, `--mc-legacy-app-bg` only 1). Recommend PR 6 treat this as a real decision point, not a footnote: either accept a genuine light-mode focus-ring color change (aliasing to `--mc-border-focus` despite the distance) or keep light's literal `#4f8cff` as a documented, deliberate exception - but don't let it get silently auto-mapped along with the other 13 just because dark's half is clean.

**6. `--mc-legacy-shadow` — confirmed distinct, not a duplicate of an existing shadow role.** Light: legacy `0 8px 24px rgba(29,53,63,.08)` vs canonical `--mc-shadow-panel` `0 2px 8px rgba(15,35,63,.045)` and `--mc-shadow-hover` `0 6px 16px rgba(15,35,63,.09)` - both blur radius and offset are meaningfully larger in the legacy value (24px/8px vs 8-16px/2-6px), consistent with "modal-scale" elevation rather than a card/hover-scale one. Dark: legacy `0 12px 30px rgba(0,0,0,.24)` - alpha coincidentally matches `--mc-shadow-panel`'s own `.24` exactly, but blur/offset still don't (30px/12px vs 10px/3px) - the alpha match is a coincidence, not a signal, same caution as note 1's light-mode exactness. Agree with the proposal: either generalize this into a new `--mc-shadow-modal` token (if this elevation scale is worth having a name for beyond this one migration) or leave `--mc-legacy-shadow` as its own un-aliased literal - don't force it onto `--mc-shadow-panel`/`-hover`.

## Summary for the brief

Independent recompute confirms the proposal's arithmetic throughout (every cross-checked number matched to within 0.1) and its two headline judgment calls (the panel/card name-vs-value swap in note 3, and keeping border/border-soft name-matched despite dark-mode drift in note 2) both hold up, with note 3 now backed by live-rendered confirmation of the actual visual consequence (an elevation-hierarchy inversion, not just a color nudge, if mapped by name) and a corrected/refined dark target for `--mc-legacy-card-bg` (`--mc-bg-muted` is technically closer than `--mc-bg-panel`, though both are safe; recommend keeping `--mc-bg-panel` for semantic clarity). One addition beyond the original table: pulled real consumer counts, which reprioritizes `--mc-legacy-focus`'s light-mode gap (14 real call sites, not a minor footnote) and quantifies the panel/card swap's true blast radius once the second compatibility layer is included (~27 sites, not 17). No token here is unmappable everywhere; 7 of 14 (workspace-bg/app-bg's mode-inconsistency footnote, border/border-soft, panel-bg/card-bg, card-hover/elevated-bg, focus) need an explicit documented decision in PR 6 rather than a silent auto-pick, consistent with the brief's own framing - this table is meant to inform that PR, not replace its judgment.
